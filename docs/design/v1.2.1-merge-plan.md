## Fork steps

1. `git switch -c release/v1.2.1 92f12598b70619dbb9af9ec4827a7660a2aea40b` in `Errantial/t3code`.
2. `git merge --no-ff feat/v1.2.1-pins-on-v1.2.0`.
3. Optional: `git merge --no-ff fix/v1.2.0-peer-test-mocks`. It changes tests only and does not affect the
   build. It merges with the pin branch without conflicts (`git merge-tree`).
4. Gates on the merged branch (see "Checks"). The merged head is the build commit.

Merge commits, not squashes, so each pin commit stays reviewable.

## Bridge steps

1. Merge `release/v1.2.0` into the bridge `release/v1.2.1`. A trial with `git merge-tree` was
   conflict-free before this re-scope; re-run it, since the docs changed.
2. Fill the release metadata in `docs/releases/v1.2.1.md` (below).
3. Bump `package.json` and `package-lock.json` to `1.2.1`.
4. Add the `v1.2.1` section to `docs/release-status.md` and the publication details to
   `docs/evidence/v1.2.1-release.md`, as for v1.2.0.
5. `npm run verify`, then an annotated tag `v1.2.1`.

## Release notes: what is script-filled

`docs/releases/v1.2.1.md` holds placeholders of the form `@@NAME@@` and lists them in a comment at the top of
the file. **All of them are values the release step produces; none needs a human decision.**

| Placeholder | Source |
| --- | --- |
| `@@BUILD_COMMIT@@`, `@@BUILD_COMMIT12@@` | head of fork `release/v1.2.1` after the merges and gates |
| `@@BUILD_DATE@@`, `@@RELEASE_DATE@@` | the build date and publication date |
| `@@FULL_VERSION@@` | `0.1.5-v1.2.1.<BUILD_DATE>.<BUILD_COMMIT12>.connect1` |
| `@@WIN_EXE@@`, `@@WIN_EXE_BYTES@@`, `@@WIN_EXE_SHA256@@`, `@@WIN_BLOCKMAP_BYTES@@` | Windows build output |
| `@@LINUX_TGZ@@`, `@@LINUX_TGZ_BYTES@@`, `@@LINUX_TGZ_SHA256@@` | Linux arm64 build output |
| `@@SOURCE_ZIP_BYTES@@`, `@@PATCH_ZIP_BYTES@@`, `@@PATCH_COUNT@@` | source and patch archives |

The check "nothing left to fill" is `grep -n "@@" docs/releases/v1.2.1.md`: only the header comment
before the tag, and nothing after the release step removes it.

## Rollback

Each fork merge is one merge commit, so the build branch can be reset or the merge reverted before
anything is published. After publication, v1.2.0 stays published and `latest` can be pointed back by
deleting the v1.2.1 release (assets are not shared with v1.2.0). There is no database migration, so
nothing needs undoing on a user's machine apart from installing the previous version.

## If swarm comes back

Merge `feat/swarm-wip` into a new branch after the pin branch. Both merge cleanly. The swarm bridge
documents are on the bridge `swarm-wip` branch.
