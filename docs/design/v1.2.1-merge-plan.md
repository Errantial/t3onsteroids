## What was checked

- Each fork branch merges onto `release/v1.2.0` with no conflicts (`git merge-tree`).
- The two branches merge with each other with no conflicts. Both add a row and a search entry in
  `LabsSettingsPanel.tsx` and `settingsSearch.ts`, and git combines them.
- The combined result is built and tested in a throwaway worktree before any real merge. Results are
  recorded in plan §9 under "Combined trial".

## Order

1. **Pins first.** It is small (24 files) and has no server or database changes. Merge
   `feat/v1.2.1-pins-on-v1.2.0` into `release/v1.2.0`.
2. **Swarm second.** Merge `feat/v1.2.1-on-v1.2.0` into the result. It is 87 files, adds migrations
   076 to 078, and carries the Labs flag. With the flag off it changes no behavior.
3. Use a merge commit for each, not a squash. The swarm branch has 58 commits whose messages are
   the history of the review rounds, and each commit was built and checked in order.

Either order gives the same tree. Pins first lets the pin work ship even if the swarm work waits for
its live runs.

## Before merging

- [ ] `release/v1.2.0` has not moved since `92f12598b7`. If it has, redo the `git merge-tree` check
      for both branches and re-run the combined trial.
- [ ] Migration numbers: `release/v1.2.0` ends at 075. The swarm branch adds 076, 077 and 078. If
      v1.2.0 adds a migration, renumber ours above it and re-run the migration tests.
- [ ] The agent context budget: `mcpToolListJsonBytes` is 57,907 with the flag off, and
      `mcpToolListJsonBytesSwarmV2` is 69,942. If v1.2.0 changes its tool list, re-measure both.
- [ ] Live runs are done or waived (see "Still blocked" in plan §9). The swarm panel and sidebar chip
      have not been seen in a browser.
- [ ] The release notes `docs/releases/v1.2.1.md` have no `TBD` left.

## After merging

- [ ] On the merged `release/v1.2.0`: `pnpm install --frozen-lockfile`, `pnpm typecheck`,
      `pnpm lint`, `pnpm knip:check`, `node scripts/release-smoke.ts`, the web production build, and
      the contracts, client-runtime, mobile and swarm server suites.
- [ ] The flag-off tool list equals v1.2.0's byte for byte: same sha256 of the listed tools.
- [ ] A database written by `release/v1.2.0` opens and migrates (76, 77, 78 only).
- [ ] Bridge: `npm run verify`, the version bump to `1.2.1`, `docs/release-status.md`, and an
      evidence file `docs/evidence/v1.2.1-release.md`, as for v1.1.9.
- [ ] Tag and build artifacts only after all of the above, and after approval.

## If v1.2.0 moves before the merge

Rebase rather than merge the 58 swarm commits only if conflicts are large. The first rebase of
this work onto `release/v1.2.0` was done by cherry-picking each commit with `-x`, comparing each
resolved pick with its original. That worked because only seven files conflicted in a trial merge
and none were swarm files. If the swarm files themselves conflict, stop and review the conflict
before resolving it.

## Rollback

Each merge is one merge commit, so `git revert -m 1 <merge>` removes it. The swarm migrations are
additive tables only: a database that ran 076 to 078 keeps unused tables if the swarm work is
reverted. A probe on the older peer-exec base found that the v1.2.0 migrator ran and started on such
a database, but its service preflight blocked on 76 to 78 and refused a switch back. That has not
been re-checked on this line, so a downgrade is unverified (plan §8.1).

## Not in this plan

- Peer-exec and the fleet tools. Their migration (074) is not on this line.
- Pushing anything to `pingdotgg/t3code`. The `upstream` push URL is disabled and stays that way.
