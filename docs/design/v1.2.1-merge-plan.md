## Fork steps

1. `git switch -c release/v1.2.1 92f12598b7` in `Errantial/t3code`.
2. `git merge --no-ff feat/v1.2.1-pins-on-v1.2.0`. Pins first: small, no server or database changes.
3. `git merge --no-ff feat/v1.2.1-on-v1.2.0`. Swarm second: 93 files, migrations 076 to 078.
4. Decide `fix/v1.2.0-peer-test-mocks` (see below). It is not needed to build or ship.
5. Gates on the merged branch (see "Checks"). The merged head is the build commit.

Merge commits, not squashes: the swarm branch is 71 commits whose history is the review record, and
each was built and checked in order. Either order merges without conflicts (`git merge-tree`).

## About `fix/v1.2.0-peer-test-mocks`

It changes tests only. It fixes 25 failures in `RemoteDelegation` and `PeerForwarding` that already
fail on the published v1.2.0 (stale mocks left by commit `631de93325`). v1.2.0's own release notes
recorded one `PeerForwarding` failure as known and excluded. Merging it is optional and not a v1.2.1
requirement. If it is merged, `release/v1.2.1` has a green peer suite where v1.2.0 did not. 5
Windows-only failures remain with it (2 `OrchestratorMcpToolkit.integration`, 2 `agentScope`, 1
`DatabaseMaintenance`).

## Bridge steps

1. Merge `release/v1.2.0` into the bridge `release/v1.2.1`. A trial with `git merge-tree` is
   conflict-free. This brings v1.2.0's release notes, `release-status.md`, the v1.2.0 evidence, and
   `package.json` 1.2.0.
2. Fill the release metadata in `docs/releases/v1.2.1.md` (below).
3. Bump `package.json` and `package-lock.json` to `1.2.1`.
4. Add the `v1.2.1` section to `docs/release-status.md`, and write `docs/evidence/v1.2.1-release.md`
   publication details, as for v1.2.0.
5. `npm run verify`, then an annotated tag `v1.2.1`.

## Release notes: what is script-filled and what is decided

`docs/releases/v1.2.1.md` holds placeholders of the form `@@NAME@@` and lists them in a comment at
the top of the file. **All of them are values the release step produces; none needs a human
decision.**

| Placeholder | Source |
| --- | --- |
| `@@BUILD_COMMIT@@`, `@@BUILD_COMMIT12@@` | head of fork `release/v1.2.1` after the merges and gates |
| `@@BUILD_DATE@@`, `@@RELEASE_DATE@@` | the build date and publication date |
| `@@FULL_VERSION@@` | `0.1.5-v1.2.1.<BUILD_DATE>.<BUILD_COMMIT12>.connect1` |
| `@@WIN_EXE@@`, `@@WIN_EXE_BYTES@@`, `@@WIN_EXE_SHA256@@`, `@@WIN_BLOCKMAP_BYTES@@` | Windows build output |
| `@@LINUX_TGZ@@`, `@@LINUX_TGZ_BYTES@@`, `@@LINUX_TGZ_SHA256@@` | Linux arm64 build output |
| `@@SOURCE_ZIP_BYTES@@`, `@@PATCH_ZIP_BYTES@@`, `@@PATCH_COUNT@@` | source and patch archives |

Decisions that were open are closed in the notes: peer-exec is out, the live runs are done on
Windows, and the release lists its documented limits (Linux provider-backed run, mobile pin check,
detach on providers that steer wakes, real three-account capacity, and downgrade to v1.2.0 are not
qualified). The "no TBD left" check is therefore: **only the `@@...@@` placeholders listed in the
file's header comment remain before the tag, and none remains after the release step.** Check it
with `grep -n "@@" docs/releases/v1.2.1.md` (only the header comment before the tag, nothing after).

## Rollback

Each fork merge is one merge commit, so the build branch can be reset or the merge reverted before
anything is published. After publication, v1.2.0 stays published and `latest` can be pointed back by
deleting the v1.2.1 release (assets are not shared with v1.2.0). The swarm migrations add tables
only. A probe on the older peer-exec base found that the v1.2.0 migrator ran and started on a
database with migrations 76 to 78, but its service preflight blocked on them and refused a switch
back. That has not been re-checked on this line, so downgrading a migrated database is unverified.

## Not in this plan

- Any push to `pingdotgg/t3code`. The `upstream` push URL is disabled and stays that way.
- Fleet rollout of v1.2.1 to any machine. That waits for explicit approval after publication.
