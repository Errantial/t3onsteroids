## 3. Item 2 — Pinned threads fold into Working when the overhaul is on

The v1.2.0 plan (§1.3) lists "Pinned working threads folded into Working" as **on hold until the
mobile behavior is checked and Emil asks for it**. This item is that request, so the mobile check
is part of the work, not a precondition.

### Target behavior (pin overhaul on, Working section on)

- A pinned thread that is working or monitoring sits in **Working**, sorted by last send like every
  other working thread.
- When it stops, it returns to the activity list with the same 2-second exit grace and "returned"
  ordering as an unpinned thread.
- No pinned section exists. Pinned threads are ordered by activity, exactly like unpinned threads.
- Pinning still blocks automatic settling. Settle stays hidden for pinned threads in every section,
  Working included. MCP's explicit settle is unchanged.
- Snoozed and Settled still take precedence, as today.
- `pinOrderKey` is kept but unused while the overhaul is on, so turning the overhaul off restores
  the user's manual pinned order.
- With the overhaul **off**, nothing changes: the pinned section stays on top and pinned threads
  never fold into Working.

### What the code does today (`feat/v1.2.0-peer-exec`)

- **Web partition** (`apps/web/src/components/Sidebar.tsx` `partitionSidebarThreads`): with the
  overhaul on, `resolveSidebarThreadSection` returns `active` for a pinned thread, which then goes
  through `inbox()`, so a working pinned thread **should already land in Working** on web. First
  task: reproduce what Emil sees before changing anything (§3.1).
- **Inbox tracker** (`packages/client-runtime/src/state/threadInbox.ts` `observe`): every
  `pinnedAt != null` thread is `excluded` from the exit-grace hold. Under the overhaul, a pinned
  thread therefore leaves Working the instant it stops, with no grace, so it can flicker between
  sections around run continuations. The exclusion must depend on the overhaul flag.
- **Mobile** (`apps/mobile/src/features/threads/threadListV2.ts` ~line 695): `pinnedAt != null` is
  checked before Working, unconditionally. Mobile does not read `sidebarPinnedThreadsOnTop` at all,
  so mobile always shows a pinned section and never folds pinned threads into Working.
- **Boring sidebar**: has no Working section. Its Labs copy says "Pinned threads stay on top".
  Proposed: leave it as is (D2).

1. **Reproduce (W2a).** On a dev server with the overhaul on, start a turn in a pinned thread and

## 4. Item 3 — Swarm v2

This section was revised on 2026-11-04 after a research pass covering published evidence, comparable
products, and this machine's own delegation history. Sources are listed in §8. Corrections to the
first draft are marked **(corrected)**.

### What v1.1.8 ships (checked against `feat/v1.2.1`)

- **Launch:** `/swarm`, the command palette, and the draft hero write an architect brief
  (`swarmBrief.ts`). The architect calls `create_swarm` once.
  `create_swarm` (`toolkits/orchestrator/handlers.ts:42-104`) checks only that member keys are unique,
  then calls `delegateTask` **one member at a time** (`concurrency: 1`, line 76), with up to **12**
  members (a schema-only limit, `tools.ts:212`). It returns `{ title, launched, failed }` with no
  swarm id.
- **Serial per-member work:** `delegateTask` (`OrchestratorMcpService.ts:2255-2453`) needs an active
  parent run. It resolves the parent HEAD with git for each worktree member (2319-2346) and runs
  `threadLaunch.prepareRun` inline (2401-2406). All of this happens inside the serial loop. In the
  local runs below, launches came 9-17 s apart, so 48 members would take 8-13 minutes just to start.
- **Wakes are already batched (corrected).** `Orchestrator.ts:11650-11803` keeps one
  `delegatedCompletion` group per parent run. A completion that arrives while the wake run is still
  queued is added to the same wake message. `delegatedCompletionWakeDetail` (689-707) inlines results
  up to `DELEGATED_RESULT_INLINE_BYTES = 16_000` and points to `task_status` for anything past that.
  Once the parent's turn starts, later completions begin a new group.
- **Task results are uncapped.** `task_status` returns the child's full last assistant message
  (`subagentProjection.ts:168`).
- **`task_cancel`** checks that every descendant can be stopped before stopping any of them
  (2484-2506), so it is all-or-nothing per task. It also covers remote tasks.
- **No admission queue (corrected).** `queueHeld` (`Orchestrator.ts:1535-1558`) holds one thread's
  own follow-up runs after a provider failure. It cannot queue member launches.
- **No provider concurrency or rate-limit handling.** `ProviderUsageLimitsIngestion.layer` is
  `Layer.empty`. The per-provider usage readers exist for display only; nothing in the delegation
  path reads them.
- **Remote placement already exists in part:** `delegateTask` routes to `remoteDelegation.delegate`
  when `target.environmentId` is set (2256-2271).

### What local use shows

No `create_swarm` run exists in the thread store yet. The large runs so far were made with
`delegate_task` alone:
- **28 children** (disk-usage CLI project, 2026-11-04), in waves of 5-8:
  - Five Opus implementers were stopped at about 8 minutes and relaunched by hand on DeepSeek v4.1
    Flash with worktrees.
  - All five reruns failed at the same instant, about 80 minutes in, on "The OpenCode event stream
    was lost and could not reconnect", followed by "Stopped by user". That points to one
    provider-server event, not five separate failures.
- **25 children** (election monitor project), all successful:
  - 14 Opus children launched about 3 minutes apart in total, one by one.
  - 11 Sonnet "finish …" children followed, which suggests the first wave left work unfinished and
    the parent handed out the rest.
- **9 DeepSeek verification children** ("Verify load-bearing claims", "Check final numbers").

These runs point to four needs:
- Waves of 5-14 members, not single 48-member launches.
- Relaunching remaining or failed work, sometimes on another provider.
- Treating a provider-instance failure as one event.
- Verification members as a pattern you already use.

### What the evidence says (summary; details in §8)

- **Parallelism pays when work is parallelizable and checked.**
  - Google Research measured 180 configurations. Multi-agent setups gained about 81% on
    parallelizable work and lost 39-70% on strictly sequential work.
  - Independent agents amplified errors up to 17.2×, against 4.4× with a central orchestrator.
- **Cost is the main lever and the main risk.** Anthropic's multi-agent research system used about
  15× the tokens of a chat, and token count explained about 80% of the performance variance.
  Anthropic also says coding parallelizes less well than research.
- **Verification is where most value and most failures are.**
  - MAST's 1,600+ failure traces cluster in system design (about 44%), inter-agent misalignment
    (about 32%) and verification (about 24%).
  - Adding an objective verification step gave +15.6% in the paper's tests.
  - Anthropic's 16-agent C compiler depended on near-perfect tests and a known-good reference
    compiler. Without them, agents collided on the same bug and undid each other's fixes.
- **Best-of-N with a check is the best-supported parallel pattern for coding.** Repeated
  sampling on SWE-bench Lite went from 15.9% with 1 sample to 56% with 250. Selection needs a
  verifier; voting plateaus. Cursor ships this as `/best-of-n`.
- **Flat peers with locks scale badly.** Cursor reports that "twenty agents would slow down to the
  effective throughput of two or three" with locks. Its planner → worker → judge hierarchy with
  isolated work did better, and a dedicated integrator role became a bottleneck.
- **Team size:** Anthropic and the Claude Code team docs recommend 3-5. Practitioners report merge
  and supervision friction from about 5 agents. No source supports 48 for coding.
- **Debate** does not beat voting at equal compute. **Peer-to-peer messaging** multiplies conflicts.
  Neither is planned.

### Goal

Run swarms that are **checked, cheap to supervise, and able to scale in waves**. Swarm v2 builds on
the existing delegated-task path and child threads; it does not add a second orchestration engine.
Delegating to one or two agents does not change. The architect stays the only hub. There is no
member-to-member messaging, shared board, or debate mode.

### Design

**S1. Swarm record (`swarm-v1` contract).**
- `create_swarm` returns a `swarmId` and persists the record server-side, in one migration
  (`076_…` or later).
- The record holds: title, architect thread, shared context reference, policies, and members. Each
  member has a key, title, role or profile, target or pool, isolation, `dependsOn`, `verify`,
  `budget`, taskId, childThreadId, instance, status, and result envelope.
- Statuses are `pending → queued → running → claimed_done → verified | failed | cancelled |
  blocked`. Claimed and verified are kept apart (see S12).
- MCP tools:
  - `swarm_status(swarmId)`: paged roster, queue positions, envelopes.
  - `swarm_cancel(swarmId, keys?)`: reuses the `task_cancel` path. Because that check is
    all-or-nothing per task, the result reports which members were stopped and which were not.
  - `swarm_retry(swarmId, keys, target?)`: optionally retries on another instance or pool. The
    retry carries the member's last envelope and is labelled as a context reset.
  - `swarm_add_members(swarmId, members)`: adds the next wave to a running swarm.
- **Crash recovery:** after a restart, running member threads are re-attached. Members that were
  admitted but never started go back in the queue. Wakes are idempotent, so a restart never
  launches a member twice.
- Existing `create_swarm` callers keep working; the new fields are optional.

**S2. Admission scheduler.**
- **Member queue:** members past a cap wait as `queued` in a new member-level queue (corrected:
  `queueHeld` cannot do this). The scheduler must not confuse that state with a member thread's own
  held runs.
- **Limits:** global, per provider instance, and per environment, from settings. A swarm can lower
  a cap but never raise it.
- **Parallel launch:**
  - Launch in parallel up to the cap.
  - Resolve the parent HEAD once per swarm instead of once per member.
  - Move `prepareRun` and worktree preparation off the serial path, so launch time no longer grows
    with member count.
- **Failure classes:** classify provider failures, building on the existing `failureClass` near
  `Orchestrator.ts:1540`:
  - **Quota or rate limit:** pause that instance's queue with backoff.
  - **Instance down** (for example, "OpenCode event stream lost"): if several members on one
    instance fail within a short window, record one instance event, pause that instance, and offer
    `swarm_retry` on another instance or pool. Do not count it as N separate failures.
  - **Task failure:** this member only.
  - Other providers keep running. Nothing guesses at quotas a provider does not report.
- **Instrumentation:** record queue wait, failure classes, and per-instance throughput (ids and
  counts only). This data sets the defaults and decides whether S11 and S8 are worth building.
- **Size (changed):** keep 12 members per `create_swarm` call by default. Larger swarms are built in
  waves through `swarm_add_members`, with a per-swarm total cap (D5). Raise the per-call cap only
  if the load test shows it helps.

**S3. Shared context and role profiles.**
- `create_swarm` takes an optional `sharedContext`, stored once and delivered to each member through
  the v1.1.6 per-turn context contributor registry, with its own `maxBytes`. It should hold the brief,
  the interface contract between members (names, file ownership, API shapes; Cognition's main point
  against parallel writers), constraints, and the definition of done.
- **Role profiles:** named, reusable member settings (provider or pool, model, effort, isolation,
  instructions, verify command). They live in project settings and are referenced from
  `create_swarm` (`member.profile: "reviewer"`) instead of being repeated in every member. This
  replaces the first draft's "dialog presets".

**S4. Result envelopes and wake policy (rewritten).**
- **Wake policy:** add a swarm `wakePolicy` on top of the existing completion group:
  - `group`: today's behavior, and the default.
  - `all`: wake once at the end.
  - `failure`: wake on the first failure, then at the end.
  - `quorum:N`: wake after N members finish.
  - A blocked member and a failure carrying its error text always wake the architect promptly
    (Devin and Claude teams both do this).
- **Envelope (data, never instructions):**
  - Contents: status, verify result, a summary of at most 2 KB, the decisions made, the assumptions,
    the artifacts (branch, commit, changed paths, PR URL), and a flag when test files changed.
  - It never contains repository contents or tool bodies.
  - The architect receives envelopes labelled as data. Text inside an envelope cannot approve
    anything or grant consent (the same rule Claude Code applies to subagent output).
- **Size cap:** `task_status` gains an optional cap so a 48-member read stays bounded. The full
  transcript is still available on demand through `t3_thread_read`.
- `swarm_collect(swarmId, since?)` returns the envelopes since the last read.

**S5. Dependencies.**
- `dependsOn: [keys]`, checked for cycles before anything launches.
- A member starts when its dependencies reach `verified` (or `claimed_done` when no `verify` is set),
  and it receives their envelopes as context.
- A failed dependency marks its dependents `blocked`.
- Keep dependency chains short: evidence shows sequential multi-agent chains lose to one agent.

**S6. Integration check (replaces the conflict report).**
- **Before launch:** members that write code declare the paths they own. The server lints the
  roster for overlapping ownership and overlapping scope, and warns the architect.
- **After members finish:**
  - Merge the member branches, in order, into a temporary integration branch.
  - Report textual conflicts.
  - Run the swarm's `verify` command on the merged result, which catches semantic conflicts that
    git merges cleanly.
- **Collision detector:** if members keep touching the same files or failing on the same error,
  pause new launches and tell the architect to re-partition (the C compiler kernel-build lesson).
- No automatic merge to the user's branch, and no dedicated integrator role. The architect, or a
  member it chooses, resolves conflicts.

**S7. UI.**
- **Swarm panel** on the architect thread: a roster board with each member's role or profile, the
  instance, provider/model/effort, status (claimed and verified shown separately), queue position,
  elapsed time, cost or tokens where reported, and the envelope summary. Per-member Stop, Retry,
  Retry elsewhere, and Open; Stop all.
- **Race view** for S14.
- **Sidebar:** members stay under the architect. The architect's Working row shows
  `Swarm 7/20 · 3 queued · 1 failed`.
- **Dialog:** a team cap, wake policy, shared context, role profiles, a verify command, and a cost
  preview (S9).
- **Mobile:** the Working row text and a read-only roster.

**S8. Fleet placement (needs v1.2.0 W3-W5).** Remote placement partly exists already. A
`placement: "spread"` option fills linked environments by their free capacity from S2. It is
Labs-only and depends on v1.2.0 W5 and the S2 instrumentation. If v1.2.0 drops W3/W4, S8 moves
to v1.3.

**S9. Budgets and safety.**
- **Per-member and per-swarm limits:** wall clock, turns, and a repeated-step detector (MAST's largest
  failure mode, at 15.7%, is step repetition). Hitting a limit stops the member; it is not a warning.
- **Fresh start:** a member that runs too long can be restarted from its envelope with a new brief,
  as Cursor does.
- **Token and cost budgets** apply only where the provider reports usage. A budget requested for a
  provider that does not report usage fails with `invalid_request`; it is not estimated.
- **Cost preview** in the dialog: members × profile × the provider's recent per-turn usage, where
  that usage is known. Otherwise it says the cost is unknown.
- **Nesting:** default depth 1, meaning members may delegate but may not start swarms, unless the
  architect allows it for a member. Nested work counts against the root swarm's limits.
- **ChatGPT/CoS:** the scheduler uses the capacity the bridge advertises, which is one active turn
  per admission lease.
- **Logging:** logs record ids, counts, statuses, and failure classes only. Never prompt text, shared
  context, envelopes, or tool bodies.

**S10. MCP context budget.** The new tools appear only while the Labs flag `labs.swarmV2` is on.
With the flag off, the tool list is byte-identical to v1.2.0, enforced by the agent context budget
test.

**S11. Provider pools (multiple accounts or providers for one model).** A pool groups provider
instances that serve the same model so a swarm can use their combined capacity.
- **Already in the fork:**
  - Several instances of one driver can run side by side, each with its own environment, config,
    and credentials. `ProviderRegistry.ts`: "Accounts can share an installation, but discovery must
    use each instance's own executable, environment, and credentials".
  - The OpenCode driver merges the instance environment into the server it starts.
  - `readOpenCodeGoUsageLimits` reads that instance's account through its `XDG_DATA_HOME` and
    reports the 5-hour, weekly, and monthly windows (percent used, reset time).
  - So three instances with separate `XDG_DATA_HOME` folders are three isolated accounts with live
    headroom.
- **Pool setting:** `providerPools: { <poolId>: { instances: [...], model, perInstanceConcurrency,
  overflow?: [...] } }`.
  - The server refuses a pool whose instances use different drivers or do not all offer the model.
    It does not fall back to a different model.
  - `overflow` lists pay-per-token instances (for example, a DeepSeek or OpenRouter API key). They
    are used only when every primary instance is full, and they count against the S9 budget.
- **Targeting:** `target.pool: "<poolId>"` on swarm members, profiles, and `delegate_task`.
  `orchestrator_capabilities` lists pools with their instances and current headroom.
- **Placement (S2):**
  - Skip instances that are erroring, signed out, paused by a failure-class event, or at their cap.
  - Prefer the most remaining 5-hour headroom, then the fewest active members.
  - If every instance is full, the member stays `queued` with the reason named.
  - Providers with no usage windows are placed by active count only, and the status says so.
  - Pools also give S14 races model or account diversity for free.
- **Stickiness:**
  - A member thread stays on its first instance for its whole life. Its session and history live in
    that instance's server and data folder.
  - If an account hits its limit mid-run, that member pauses or fails with the reason. Only members
    that have not started move elsewhere.
  - `swarm_retry` on another instance starts fresh from the last envelope.
- **Visibility:** the roster shows each member's instance. The usage page shows each account and
  the pool total. Credentials stay in each instance's data folder or `settingsSecrets`. Logs carry
  instance ids only.
- **Provider terms:**
  - Some subscriptions (possibly including OpenCode Go; not yet checked) forbid using several
    accounts to get around per-account limits.
  - The settings UI states that the user is responsible for the terms.
  - The documented examples are one subscription plus pay-per-token overflow, the same model from
    different providers, and team or organization accounts.
- **Evidence gate:** no source measures multi-account pooling. Ship it once the S2 instrumentation
  shows that queue wait or quota pauses are the bottleneck.

**S12. Verification contract (new).**
- **Per member, or per profile or swarm:** `doneCriteria`, a short text, and an optional `verify`
  command, such as tests or a build.
- **When a member says it is done:**
  - The server runs `verify` in the member's checkout and records pass or fail in the envelope.
  - A failure goes back to the same member as a new turn with the output's last lines, up to
    `maxVerifyRetries` (default 2), before the architect is woken.
  - The member's status is `claimed_done` until verify passes, then `verified`.
- **Changed test files:** if a member changed test files, the envelope flags it. With
  `protectTests`, verify runs the swarm base's copy of those tests. This guards against agents
  editing tests to pass, which METR reports.
- **Optional reviewer:** a `reviewer` profile member that `dependsOn` a writer and runs its own
  checks. This is what you already do by hand with "Verify …" children.
- **Precedent:** Claude agent teams (`TaskCompleted` hook veto), Jules (critic), Conductor (checks),
  MAST (+15.6% from verification).
- **Command safety:** verify commands run under the member's runtime mode and permission policy.
  Nothing is escalated.

**S13. Architect brief and decomposability (new; prompt and tool description only).**
- The brief asks the architect, before it designs a roster:
  - Is the work parallelizable?
  - What is each member's verify step?
  - Which files does each member own?
- It says to use one agent or a short chain for sequential work.
- Defaults: 3-5 members per wave and at most 12 per call. Later waves go through
  `swarm_add_members`.
- Read-only "investigator" members are the cheap default for research. Writers get the
  interface contract in `sharedContext`.
- The `create_swarm` tool description repeats the gate, so agents calling it directly (without the
  dialog) see it too.
- Costs nothing at runtime; addresses MAST's system-design failures and Google's sequential-task
  penalty.

**S14. Race mode (best-of-N, new).**
- `create_swarm({ race: { task, attempts: [targets or pools], verify, select: "first_verified" |
  "all_then_compare" } })`.
- Launches N worktree members on the same task with different models, instances, or efforts.
- `verify` (S12) is required, because selection without a check is unsupported by the evidence.
- The race view shows each attempt's verify result, diff size, time, and cost. The user or
  architect picks a winner. Losing worktrees are discarded on confirmation and their branches are
  kept for 7 days.
- Pools (S11) give account or model diversity cheaply.

**S15. Batch map (new).**
- `create_swarm({ map: { template, rows: [...], profile } })` starts one member per row, with the row
  substituted into the template.
- It is for many similar small tasks, for example "migrate each of these 30 files" or "review each
  package".
- The scheduler queues the rows; results come back as one table through `swarm_collect`.
- Comparable to Codex `spawn_agents_on_csv` and LangGraph `Send`.

**S16. Worktree setup (new).**
- A project-level `swarm.setup` script (install dependencies, copy env files) runs once per member
  worktree before the member's first turn.
- `T3_SWARM_PORT_BASE` gives each worktree its own port range, so parallel test servers do not
  collide. Conductor and Cursor do the same.
- A failed setup marks that member `failed` (class: setup) and does not start the agent.
