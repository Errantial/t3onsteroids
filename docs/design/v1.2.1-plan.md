## 2. Item 1 — Move the pin overhaul to Labs

  (`apps/web/src/components/settings/SettingsPanels.tsx` ~line 893), under **Working section**.
- It is stored as `sidebarPinnedThreadsOnTop` (default `true`, `packages/contracts/src/settings.ts`
  line 494). The switch is labelled "Labs pin overhaul", but it is inverted: **on means the old

  points at `/settings/general`.

   placed directly after the boring-sidebar rows.

   !sidebarPinnedThreadsOnTop`. Description: "Pinned threads sort with activity and fold into

5. Remove it from the General panel's changed-settings summary and its reset (lines ~470 and ~638),

6. Docs: update `docs/user` (sidebar/settings) and the release notes.

## 3. Item 2 — Pinned threads fold into Working when the overhaul is on

The v1.2.0 plan (§1.3) lists "Pinned working threads folded into Working" as **on hold until the
mobile behavior is checked and Emil asks for it**. This item is that request, so the mobile check
is part of the work, not a precondition.

### Target behavior (pin overhaul on, Working section on)

- A pinned thread that is working or monitoring sits in **Working**, sorted by last send like every
  other working thread.
- When it stops, it returns to the activity list with the same 2-second exit grace and "returned"
  ordering as an unpinned thread.
- No pinned section exists. Pinned threads are ordered by activity, exactly like unpinned threads.
- Pinning still blocks automatic settling. Settle stays hidden for pinned threads in every section,
  Working included. MCP's explicit settle is unchanged.
- Snoozed and Settled still take precedence, as today.
- `pinOrderKey` is kept but unused while the overhaul is on, so turning the overhaul off restores
  the user's manual pinned order.
- With the overhaul **off**, nothing changes: the pinned section stays on top and pinned threads
  never fold into Working.

### What the code does today (`feat/v1.2.0-peer-exec`)

- **Web partition** (`apps/web/src/components/Sidebar.tsx` `partitionSidebarThreads`): with the
  overhaul on, `resolveSidebarThreadSection` returns `active` for a pinned thread, which then goes
  through `inbox()`, so a working pinned thread **should already land in Working** on web. First
  task: reproduce what Emil sees before changing anything (§3.1).
- **Inbox tracker** (`packages/client-runtime/src/state/threadInbox.ts` `observe`): every
  `pinnedAt != null` thread is `excluded` from the exit-grace hold. Under the overhaul, a pinned
  thread therefore leaves Working the instant it stops, with no grace, so it can flicker between
  sections around run continuations. The exclusion must depend on the overhaul flag.
- **Mobile** (`apps/mobile/src/features/threads/threadListV2.ts` ~line 695): `pinnedAt != null` is
  checked before Working, unconditionally. Mobile does not read `sidebarPinnedThreadsOnTop` at all,
  so mobile always shows a pinned section and never folds pinned threads into Working.
- **Boring sidebar**: has no Working section. Its Labs copy says "Pinned threads stay on top".
  Proposed: leave it as is (D2).

### Work

1. **Reproduce (W2a).** On a dev server with the overhaul on, start a turn in a pinned thread and
   record which section it is in while running, during a continuation, and after it stops. Do the
   same on mobile. Write down the gaps; this may shrink the web half to the tracker fix.
2. **Shared rule.** Add one pure helper in `client-runtime` (e.g. `resolveInboxShelf({ pinned,
   pinnedOnTop, working, snoozed, settled })`) and use it in web `partitionSidebarThreads`, mobile
   `threadListV2`, and the tracker's `excluded` check. Web and mobile then cannot drift.
3. **Tracker.** `observe` takes `pinnedOnTop`. A pinned thread is excluded from the grace hold only
   when `pinnedOnTop` is true. Include the flag in the tracker's cached result key so toggling it
   rebuilds the list.
4. **Mobile.** Read the setting on mobile (D3 decides where it comes from), apply the shared rule,
   hide Settle for pinned threads under the overhaul (matching web's `settlementSupported` check),
   and keep `ThreadArrangementSheet` pin reordering available only with the overhaul off.
5. **Drag and drop (web).** Working rows stay non-droppable. Dropping onto the activity list with
   the overhaul on must not create a pinned section. Re-run the existing Sidebar drag tests.
6. **Interaction with "Working section at top"** (`plan/working-shelf-position`, still unshipped):
   no extra work, but if it lands first, test both positions.

### Tests

- `Sidebar.logic.test.ts` and `threadListV2.test.ts`: a pinned working thread goes to Working with
  the overhaul on and to Pinned with it off; the snoozed and settled precedence; sort by send in
  Working and by activity after return.
- `threadInbox` tests: a pinned thread gets the exit grace under the overhaul and does not get it
  with the overhaul off; toggling the flag rebuilds the placement.
- Manual check on web through the background-browser path and on mobile: a long-running pinned
  thread, a run with a continuation, a pinned thread that becomes actionable (approval or question)
  while working, and the overhaul toggled while a pinned thread is working.

## 4. Item 3 — Swarm v2

### What v1.1.8 ships

- `/swarm`, the command palette, and the draft hero open a dialog that writes an architect brief.
  The architect calls `create_swarm` once.
- `create_swarm` (`apps/server/src/mcp/toolkits/orchestrator/handlers.ts`) is a thin loop over
  `delegateTask`, run **one at a time** (`concurrency: 1`), with up to **12** members, all
  `mode: "async"`. A failed launch is reported in `failed`.
- There is no swarm record: no id, no status call, and no swarm-wide stop or retry. The parent's
  Stop is the only swarm-wide control.
- Every member starts immediately. Nothing limits how many run at once per provider, machine, or
  account.
- Each member is woken on its own, so the architect reads N separate results into its context.
- Shared background is copied into every member's task text, so the architect writes it N times and
  every member pays for it.
- No dependencies between members, no phases, and no help integrating worktree branches.

### Goal

Run swarms of dozens of members reliably, at lower token cost, with one place to see and control
them. Swarm v2 builds on the existing delegated-task path and child threads; it does not add a
second orchestration engine. Delegating to one or two agents does not change.

### Design

**S1. Swarm record (`swarm-v1` contract).** `create_swarm` returns a `swarmId` and persists it:
title, architect thread, shared context reference, policies, and members (key, title, role,
target, isolation, `dependsOn`, taskId, childThreadId, status, result envelope). Statuses:
`pending → queued → running → completed | failed | cancelled | blocked`. Stored server-side (one
migration, `076_…` or later) so it survives restarts. New MCP tools:
- `swarm_status(swarmId)`: the roster with status, queue position, and result summaries, paged.
- `swarm_cancel(swarmId, keys?)`: cancels the whole swarm or named members, using the exact
  `task_cancel` semantics.
- `swarm_retry(swarmId, keys)`: relaunches failed or cancelled members with the same task.
- `swarm_add_members(swarmId, members)`: grows a running swarm.
Existing `create_swarm` callers keep working; the new fields are optional.

**S2. Admission scheduler (the capacity work).** Members past a cap wait as `queued` instead of
all starting at once.
- Limits: global, per provider instance, and per environment. They come from settings, with
  defaults sized from measurement. A swarm can set a lower cap, never a higher one.
- Launches run in parallel up to the cap instead of `concurrency: 1`.
- The per-call member cap rises from 12 to a measured number (D5 proposes 48), and
  `swarm_add_members` covers larger work.
- A provider rate-limit or quota error pauses that provider's queue with backoff, and the swarm
  status names the reason. Other providers continue. The scheduler does not guess at quotas a
  provider does not report.
- It reuses the existing queued-run machinery (`queueHeld`, queued-run cancel) where it fits.

**S3. Shared context once.** `create_swarm` takes an optional `sharedContext` (the brief,
constraints, repo facts, the definition of done), stored once on the swarm record. It is delivered
to each member through the v1.1.6 per-turn context contributor registry, with its own `maxBytes`,
instead of being pasted into every task. The architect writes it once, and providers with prompt
caching can reuse the identical prefix. A member's `task` stays self-contained apart from that block.

**S4. Result envelopes and batched wakes.** Each member ends with a bounded result envelope:
status, a summary of 2 KB or less, and artifacts (branch, commit, changed paths, PR URL). The
envelope never contains repository contents or tool bodies. A swarm `wakePolicy` decides when the
architect wakes: `each` (today's behavior), `batch` (every N completions or T seconds), `all`
(once, at the end), or `failure` (on the first failure, then at the end). The default for new
swarms is `batch`. `swarm_collect(swarmId, since?)` returns the envelopes since the last read, so
the architect reads one digest instead of N transcripts.

**S5. Dependencies and phases.** Members may list `dependsOn: [keys]`. The server validates that
the graph has no cycles before launching anything and starts a member when its dependencies
complete. A dependent member receives its dependencies' envelopes as context. A failed dependency
marks its dependents `blocked`; they do not run. This gives fan-out → integrate → review without
the architect polling.

**S6. Worktree integration help.** For members with `isolation: "worktree"`, `swarm_status` reports
each branch's head, ahead/behind against the swarm base, and a dry-run merge conflict check
between member branches. The plan does not add automatic merging. An `integrator` member (S5) or
the architect merges.

**S7. UI.**
- **Swarm panel** on the architect thread: a roster board with each member's role,
  provider/model/effort, status, queue position, elapsed time, and the envelope summary, plus Stop,
  Retry, and Open for each member and Stop all.
- **Sidebar:** members stay under the architect, as today. The architect's Working row shows
  `Swarm 7/20 · 3 queued`.
- **Dialog:** a team cap that includes larger sizes when the scheduler is on, a wake policy choice,
  an optional shared-context field, and saved team presets (D7).
- **Mobile:** the Working row text and a read-only roster.

**S8. Fleet placement (needs v1.2.0 W3–W5).** A member may target another linked environment
(already possible through `delegate_task` once v1.2.0 adds `environmentId`). A swarm `placement:
"spread"` option fills environments by their free capacity from S2. It is Labs-only and depends on
v1.2.0 shipping W5 and the linked-environment work. If v1.2.0 drops W3/W4, S8 moves to v1.3.

**S9. Budgets and safety.**
- A per-swarm wall-clock limit and an optional turn limit per member.
- A token budget only where the provider reports usage. Elsewhere, a requested token budget fails
  with `invalid_request` and names the providers that cannot report usage; it is not estimated.
- Nested swarms count against the root swarm's limits.
- The ChatGPT/CoS provider runs one active turn per bridge admission lease. The scheduler treats
  its capacity as what the bridge advertises, not a default.
- Swarm logs record ids, counts, and statuses only. They never record prompt text, shared context,
  envelopes, or tool bodies.

**S10. MCP context budget.** The new tools grow `mcpToolListJsonBytes`. The new tools appear only
while the Labs flag `labs.swarmV2` is on. With the flag off, the tool list is byte-identical to
v1.2.0, enforced by the agent context budget test.

### Qualification for item 3

- Unit: graph validation; scheduler caps with mixed providers; backoff on a rate-limit error; wake
  batching; envelope size limits; cancel and retry exactness; persistence across a server restart
  with members queued and running.
- Load: a 24-member and a 48-member swarm on a dev server, using a mock or cheap provider, with
  wall time, peak concurrency, architect context bytes, and member prompt bytes recorded against a
  v1.1.8-style baseline (12 members, `each` wakes, inlined shared context). This measurement backs
  the efficiency claim; without it, the claim is not made.
- Live: one real swarm (5–8 members, two providers, one worktree member), checked through the
  background-browser path, not the desktop app.
- The agent context budget test passes with `labs.swarmV2` on and off.
