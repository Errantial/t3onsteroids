  - Search id `swarm-v2-beta`.
- **New MCP tools (shown only with the flag on):** `swarm_create`, `swarm_status`, `swarm_cancel`,
  `swarm_retry`, `swarm_collect`, `swarm_add_members` (SW-A3c), and `swarm_followup` (SW-A7).
- **Legacy tool:** `create_swarm` is unchanged and is hidden while the flag is on, so an agent sees
  one swarm tool at a time.
- **New server package `apps/server/src/swarm/`:**
  - `SwarmStore`: persistence.
  - `SwarmService`: create, status, cancel, retry, collect, `stopMember`, and `notifyArchitect`.
  - `SwarmScheduler`: admission, failures, and limits.
  - `SwarmVerifier`: verify runs.
  - `swarmTurnContext.ts`: the member contract contributor.
  - `SwarmEventReactor`: watches domain events.
- **No new orchestration engine.** Members are ordinary delegated child threads. Their launches use
  the existing `delegated_task.request`, through one new admission path (§4.2).

### 4.2 Launching after the architect's turn has ended

The problem has two parts:
- `delegateTask` requires the architect's run to be active (`parent_not_active`,
  `OrchestratorMcpService.ts:2283-2295`).
- `dispatchDelegatedTaskRequest` (`Orchestrator.ts:7200`) refuses a parent run that is not blocking
  (7227), that is stopping (7234), or whose node does not belong to it (7242-7253).

The architect ends its turn right after `swarm_create`, so a member that waits for a free slot
cannot be launched through today's path.

Revision 1 proposed registering every member as a deferred child parked in `preparing`. That is
dropped, because the review found:
- Restart reconciliation cancels `preparing` runs (`ProviderRuntimeRecoveryService.ts:86-95`, 219,
  468-477).
- A Stop on the architect cascades to them.
- They count as live runs (`Orchestrator.ts:643-645`), so they flood Working and show "Preparing
  workspace".
- `defer_start` without a workspace strategy is unsupported (`Orchestrator.ts:7419-7422`,
  `ThreadLaunchService.ts:1071-1072`).

**Design (revision 2): queued members do not exist in the orchestrator until they are admitted.**
- **Queued members are only rows.** A queued member is a row in `swarm_members`. Nothing about it
  exists in the orchestrator, so restarts and Working are unaffected.
- **The anchor run.** At `swarm_create`, the server records an anchor: `parentThreadId`, the
  architect's current `parentRunId`, and that run's `rootNodeId`. Members that fit the caps are
  launched right away through today's path while the run is live.
- **Late admission.** Later admissions dispatch `delegated_task.request` through a new
  **swarm-admission** variant. The command gains an optional `swarmAdmission: { swarmId }` field
  (contracts `orchestrationV2.ts` ~3290). It is accepted only when **all** of these hold:
  - `createdBy: "agent"` with `creationSource: "server"` (rev 3.3: `OrchestrationV2Actor` has no
    `"server"`; this is the pair server-created completion messages use, `Orchestrator.ts` ~5366.
    `ws.ts` (~1898-1905) overwrites `createdBy` with `"user"` but passes the client's
    `creationSource` through, so `createdBy` is the half a client cannot forge);
  - the parent run is the anchor run recorded for that swarm (the orchestrator checks it against the
    command, and `SwarmService` is the only issuer);
  - the anchor run's `delegatedCompletion.disposition` is `open`. `swarm.anchor` always creates the
    cohort, so it is never unset (rev 3.3). A Stop marks it `stopped` (below), so this one check
    replaces both the `stopReachedRun` check and the rev 2.1 interrupt-request scan;
  - the parent thread is not archived or deleted;
  - the parent node belongs to the anchor run.

  The `isBlockingRun` check is skipped only for this variant. Everything else in the dispatch is
  unchanged: the subagent row, lineage, the cohort on the anchor run, and the child message.
- **A durable anchor marker (rev 2.1).** The orchestrator cannot read `SwarmStore`, so the anchor
  must be recorded in orchestrator state.
  - `swarm_create` dispatches a new `swarm.anchor { swarmId }` command while the architect's run is
    live. It records the `swarmId` on the anchor run (`delegatedCompletion.swarmIds`, added to the
    run contract next to `orchestrationV2.ts:621-625`). This happens even when no member can be
    admitted at once, for example when every target instance is paused.
  - `swarm.anchor` is an `OrchestrationV2InternalCommand` (rev 3.3), so `dispatchCommand` cannot
    carry it at all.
  - A swarm-admission dispatch requires its `swarmId` to be present on the anchor run.
  - Every cohort rewrite keeps `swarmIds`. Two built the cohort as a literal and would have dropped
    them: the first-delivery branch of `planDelegatedCompletionDelivery` and
    `disposeDelegatedCompletionCohort`. The prototype fixes both; every other writer spreads
    `...cohort`, and `preserveRunRecordedFields` keeps the cohort across run updates.
- **Strip the field from clients (rev 2.1).** `withCreationProvenance`
  (`ThreadManagementService.ts:84-86`) already overwrites `createdBy` for client commands. It must
  also strip `swarmAdmission`, the way `linkOrigin` is stripped. That way a WebSocket client
  (`ws.ts:1876-1905`) cannot forge a late admission.
- **Stop marks the anchor (rev 3.3; replaces rev 2.1's interrupt-request scan).**
  - **Why.** `holdStoppedThread` stops only cohorts that have a delivery or an undelivered task
    (`Orchestrator.ts` ~10412-10426), so a Stop never reached an anchor whose members were all
    queued rows or delivered, not even a Stop on the live anchor itself (SW-A0 Q2). Rev 2.1
    compensated by refusing when any run at or after the anchor carried a `run_interrupt_request`.
    But three non-Stop paths write the same item, so the scan read them as a Stop and would have
    blocked admission for good (and cancelled the swarm through §4.6):
    - `/goal` (`stopRunForQueuedCommand`, ~5856 and ~9096 @ d9def9aa06);
    - "Skipped compaction to send a queued message" (~9065 @ d9def9aa06);
    - `t3_thread_interrupt` without `stop` (`ThreadManagementService.interruptThread`, ~1136), also
      used by `RemoteDelegation.ts:426`.
  - **Change.** `holdStoppedThread` also adds every run whose cohort carries `swarmIds` to
    `cohortRunIds`, so a Stop disposes those cohorts as `stopped` (keeping `swarmIds`). The guard
    checks `disposition === "open"` only, and the scan is removed. This runs inside the Stop's
    dispatch, under the parent lock that admission also takes, so a concurrent Stop cannot race it.
  - **Stop paths checked (@ d9def9aa06); all reach `holdStoppedThread`:**
    - web and mobile Stop, and the `thread.stop` keybinding: `interruptThreadTurn`
      (`client-runtime/operations/commands.ts` ~783-878) sends `thread.stop` when the server has
      the `threadStop` capability, and otherwise, or for an explicit run, `run.interrupt` with
      `holdQueue: true`;
    - `dispatchThreadStop` (~11402-11487): with a live target it runs `dispatchRunInterrupt` with
      `holdQueue: true`, whose every success path calls `stopRemainingWork` → `holdStoppedThread`
      (~10897, 11097, 11138, 11177); with no live target, or when the interrupt fails, it calls
      `holdStoppedThread` directly (~11483);
    - `run.interrupt` with `holdQueue: true` from any client, the same path;
    - MCP `t3_thread_interrupt` with `stop: true` (`OrchestratorMcpService.ts` ~3137-3160), which
      dispatches `thread.stop`.

    Child-thread stops (`stopDelegatedTasks`, `cancelTask`) also use `thread.stop`, on threads that
    carry no anchor of their own.
  - **Non-Stop paths checked; none calls `holdStoppedThread`:** the three above. All dispatch
    `run.interrupt` without `holdQueue`, whose branch stops both the interrupted run's cohort and
    the cohort its wake message belongs to (~10903-10915).
    - **Problem (rev 3.4).** During a swarm the architect's live turn is usually a wake turn, so
      such an interrupt would stop the anchor cohort and cancel the swarm. And `stopDelegatedTasks`
      is queued only by `thread.stop` (~11478), so running members would keep going against a
      stopped cohort and nothing would ever be delivered.
    - **Fix (rev 3.4, SW-A3).** The non-`holdQueue` branch of `dispatchRunInterrupt` skips cohorts
      that carry `swarmIds`. Only `holdStoppedThread` stops an anchored cohort.
    - **What happens to an interrupted wake's tasks (verified @ d9def9aa06,
      `finalizeDelegatedCompletionDelivery` ~12326-12395).** When the delivery run ends, its
      `claimed` tasks become `pending` if the run is `cancelled`, and are then gathered into a new
      delivery while the cohort is `open`, so they are re-delivered. An interrupted running wake
      ends `interrupted`, and its tasks become `delivered`; the architect already received their
      text, and they stay readable through `swarm_collect`.
    - The wake run's **own** cohort (tasks the architect delegated during that turn) carries no
      `swarmIds` and is stopped as today.
  - Archive and delete dispose the cohort (`disposed`), which also refuses admission.
  - **Prototype:** `32f249aa15` still implements the rev 2.1 scan. SW-A3 replaces it with the
    `holdStoppedThread` change and flips the Q2 test expectations from "open, refused by the scan"
    to `stopped`.
- **Failed anchor run.** If the anchor run ends `failed`, for example on a provider error right
  after `swarm_create`, admission continues. The members' work is independent of the architect's
  turn, and completions still wake the architect. A test pins this behavior.
- **Modes at admission.** The runtime and interaction modes are re-resolved against the architect
  thread's **current** modes (`delegatedTaskModes.ts`). A member never starts with more than the
  architect has now.
- **Ordering.** Admission dispatches take the parent lock (`threadDispatch.withLock`,
  `Orchestrator.ts:13052-13072`) one at a time, as today. The child's `prepareRun` and its first turn
  run outside the lock.
- **Retries.** `swarm_retry` and the panel's Retry use the same admission path, so they work with no
  live architect run. So do automatic retries (SW-A8) and `swarm_add_members` (SW-A3c).
- **Workspace preparation.** `delegateTask` calls `threadLaunch.prepareRun` itself after the
  dispatch, when the child's `run.created` carries `workspacePreparation`
  (`OrchestratorMcpService.ts:2393-2405`). The swarm-admission path is a dispatch only, so
  `SwarmService` makes the same call after each late admission. Without it, a late worktree member
  never leaves preparation.

### 4.6 What `SwarmEventReactor` watches

The reactor subscribes to `engine.streamDomainEvents`, the same source as
`DelegatedTaskQuestionReactor`. It filters to the threads of swarm members (by `child_thread_id`)
and the architect threads of active swarms. It handles:
- **Child `run.updated`:**
  - `running` → member `running`.
  - Terminal → the member terminal path (SW-A5/A6). This applies only to bound runs: the first
    run, verify retries, follow-ups (`swarm-followup:<swarmId>:<key>:<n>`, rev 3), and usage-limit
    continuations (SW-A6 run binding).
  - A failed `prepared-run.fail` frees the member's slot, and the member becomes `failed` with
    class `launch`. This includes a failed project setup script (SW-B5 note). The command carries
    only an `OrchestrationV2ProviderFailure` (`orchestrationV2.ts:3165-3170`), not the stage, so
    the plan does not promise a separate setup reason.
- **Architect thread:**
  - The anchor cohort's `disposition` becoming `stopped` (a `run.updated` on the anchor run) →
    cancel the swarm (D12). Rev 3.3: a Stop now always marks the anchor `stopped` (§4.2), so this is
    the only Stop signal. The reactor no longer watches `run_interrupt_request` items, which
    `/goal`, skipped compaction, and `t3_thread_interrupt` also write. At startup, the reactor
    recomputes this check for every active swarm, because its in-memory state is lost on restart.
    - Rev 3.4: when the reactor sees an anchor cohort become `stopped`, it calls `stopMember` for
      every launched, non-final member that is not already stopping. This is idempotent with the
      `stopDelegatedTasks` cascade, and covers any path that stops the cohort without queuing the
      cascade.
  - The cohort becoming `disposed` through a user cancelling a queued wake (`Orchestrator.ts:9284`) →
    detach the swarm (D12).
  - Archive or delete → cancel.
- **Settings changes** to caps or the flag → the scheduler re-evaluates. If the flag is turned off,
  nothing new is admitted. Running members continue, and the panel still shows them.

  in it (11684-11726), and the delivery may also hold plain `delegate_task` siblings. So release is
  bounded by bytes:
  - **Gate (rev 3.2).** The gate is **closed** while all of these hold:
    - the anchor run's `delegatedCompletion.delivery` is non-null;
    - its run (`completionDeliveryRun`, as at 11684) is missing or `queued`;
    - the delivery already holds a released swarm task.

    "Missing" covers the case where planning has created or joined a delivery whose run does not
    exist yet. Planning returns `offer: true` (11765, 11801), and the run is created later through
    `continuationRequests.offer`. While the gate is closed, ready members wait. The reactor tries
    again when the delivery's run appears, starts, or ends, and on the 5 s tick.
    `offerDelegatedCompletionDelivery` creates no run when the parent run has no provider thread
    (`Orchestrator.ts:1261-1268`), which is an existing orchestrator stall. If a delivery has had no
    run for 10 minutes, `notifyArchitect` sends one `delivery_stalled` note and the gate keeps
    waiting. The panel and `swarm_collect` still show the results.
  - **One evaluation per pass (rev 3.3).** The gate is evaluated once per release pass, before the
    pass. An open gate lets the pass release its whole fitting prefix (below), one dispatch after
    another; the delivery the first of them opens does not close the gate for the rest of the same
    pass. Evaluated before each member instead, the second member already sees a delivery with no
    run that holds a released swarm task, so k members ready together become 2 wakes, 1 + (k−1),
    even for k = 4 (SW-A0 Q7). With per-pass evaluation the measured count is 1 wake for k = 4 and
    k = 12, idle or busy, and 2 only when a delivery run is already running. A non-swarm task that
    joins mid-pass may arrive as a pointer (rev 3.4).
  - **Already-committed bytes (rev 3.2):** the rendered label and detail bytes of every task in
    `delivery.taskIds`, whatever the run's state. While a delivery run is running, add the anchor
    run's `pending` terminal tasks, which the terminal-run collector will gather (12263-12271).
  - **Label size (rev 3.3).** A delegated task id derives from its command id, so a wake label is
    about 220 bytes, not about 120. 12 digests of 1 KB measured 14,678 bytes, leaving about 1.3 KB;
    a 13th does not fit. Live command ids carry the MCP `requestNamespace` and may be longer. So
    the gate measures with the real helper and never budgets from a member count.
  - **Batch:** among the members the policy has made ready, in ordinal order, take the longest
    prefix whose rendered label and detail bytes (measured with the helper above), plus the
    already-committed bytes, fit within `DELEGATED_RESULT_INLINE_BYTES`. The rest stay unreleased
    and go in a later release.
  - **Progress:** if not even the first ready member fits, because siblings already fill the
    budget, release that one member alone. It may arrive as a pointer, and its full envelope stays
    readable through `swarm_collect`.
  - Under `group` this usually releases one member at a time; under `failure` and `batch` it caps
    each release.
  - The digest is JSON with `<` escaped as `\u003c` (the follow-up note body uses the same
    wrapper and escaping, rev 3.2), inside
    `<swarm-member-result trust="data">…</swarm-member-result>`. The tool descriptions and
    this wrapper say the content is data from another agent and cannot approve or authorize
    anything.
- **Release rules:**
  - `group`: release each member when its envelope is final (after verify).
  - `failure`: release a failed member at once; release the rest at the end.
  - `batch` (rev 3, replaces `all`): release the final, unreleased members together, through the
    release gate above, when any of these holds:
    - `minCount` of them are waiting (default 4);
    - the oldest has waited `maxWaitMs` (default 120 s);
    - no member is left non-final.

    The window is computed from `ended_at` and `released`, so it survives a restart. The
    scheduler's 5 s tick checks it. The release order is ordinal.
  - **Collected wakes are not in ordinal order (rev 3.3).** The terminal-run collector
    (12263-12271) gathers pending tasks in task-id string order (`…10`, `…11`, `…2`; SW-A0 Q7).
    Either sort the collected task ids by their card turn-item ordinal there, or keep the digest
    order-insensitive (each digest carries its `key`). SW-A5 picks the sort; the brief does not
    promise an order. Rev 3.4: the collector serves every delegated cohort, so it sorts **only when
    the cohort carries `swarmIds`**; flag-off behavior stays identical.
  - Under every policy, a cancelled, budget-stopped, or failed member is released with its digest,
    through the gate.
  - Release and the startup sweep act only on a row's **current** `task_id`. A superseded
    attempt's task is disposed instead (SW-A7).
  - A follow-up on a member that is not yet released (rev 3.1, SW-A7) replaces the pending
    envelope. The member is then released through this normal path with the new digest.
- **Architect notes (`SwarmService.notifyArchitect(swarmId, note)`):** events that are not member
  completions use a server-created message to the architect thread:
  - an instance pause (usage limit or, rev 3, instance down);
  - a swarm cancelled, budget-stopped (rev 3: including `maxTotalTurns`), or detached;
  - "N members waiting on your approval in their threads" (D6);
  - a completion delivery with no run for 10 minutes (`delivery_stalled`, once per delivery, SW-A5);
  - rev 3: a follow-up result for an **already released** member (`followup_result`, SW-A7).
    These are coalesced over 5 s rather than 30 s. One message carries the digests that fit within
    the same 16,000-byte budget, and the rest go in the next one.
    - **Outbox (rev 3.2).** Before dispatch, a `swarm_note_outbox` row records the members and
      follow-up numbers. The command id is `swarm-note:<swarmId>:followup_result:<seq>`.
    - The body wraps each digest in `<swarm-member-result trust="data">` with the same `<`
      escaping as the wake.
    - One transaction marks the row `sent` and sets `followup_notified` for its members.
    - Recovery re-dispatches unsent rows unchanged.

  The message uses `message.dispatch`, `createdBy: "agent"` with `creationSource: "server"`, and
  `queue_after_active`, like
  `DelegatedTaskQuestionReactor.wakeParent` (`:32-59`). The command id is
  `swarm-note:<swarmId>:<kind>:<seq>`. Notes are coalesced to at most one per swarm every 30 s.
  These notes do not go through the cohort, which `cancelTask` disposes
  (`OrchestratorMcpService.ts:2507-2530`).

- **Flow:**
  - Child run terminal (`completed`) → `claimed_done` → `verifying`.
  - **Pass:** `verified`, then release.
  - **Fail with retries left:** `SwarmService` dispatches a server message to the **member's** thread
    with the command, exit code, and the last 2 KB of output. The member goes back to `running`. The

    (`Orchestrator.ts:5183-5185`), and finalization skips tasks that already have a result
    (~12128-12137). The held wake is released only once, at the end.
  - **Fail with no retries left:** `failed` (class `verify`), then release.
  - A child run that ends `failed` or `interrupted` skips verify and goes straight to the failure
    path (SW-A8).
- **Run binding (rev 2.1).** The reactor acts only on runs that belong to the swarm. Each attempt is
  bound to known runs:
  - the first run is `child_run_id`;
  - each verify retry is the run created by the swarm's own message
    (`swarm-verify:<swarmId>:<key>:<n>`, stored as `bound_run_id`);
  - each follow-up is the run created by `swarm_followup`'s message
    (`swarm-followup:<swarmId>:<key>:<n>`, also stored as `bound_run_id`, rev 3, SW-A7);
  - a usage-limit continuation is linked through `usageLimitContinuationOfRunId`.

  increments `turns_used` before release and is ignored after release. Such a run never triggers
  verify or a second release.
- **Verify races (rev 2.1).** If a child run starts while verify is running, the verify is aborted
  through the `boundedExec` tree kill, its result is discarded, and the member goes back to
  `running`. The retry message is not sent if the swarm row has been cancelled or detached by then.
  This is checked against the swarm row's own state immediately before dispatch.

      - both successor collectors need `pending` (12263-12271, 12378-12387).

**SW-A8. Failure handling (2.75 d; rev 3 adds 1 d for the instance-down pause and automatic
retry; rev 3.1 adds 0.25 d).**
- **Source:** the child's failure class comes from `latestRootProviderFailure` (`Orchestrator.ts`,
  imported at 9-11), which the adapters already classify, for example
  `ClaudeAdapterV2.ts:3655-3710` for 429 errors.
- **`usage_limit`:**
  - Pause new admissions on that instance until `resetAt`, or for 15 minutes when there is no
    `resetAt`. The pause is written to `swarm_instance_pauses` with `pause_class` `usage_limit`.
  - **Auto-resume on:** the member moves to a new status, `limit_wait`, and is not marked failed.
    The existing usage-limit continuation (`Orchestrator.ts:5086+`, `UsageLimitRecoveryWorker.ts`)
    owns resuming the thread.
    - `limit_wait` frees the member's **global** slot and keeps its **per-instance** slot. That
      instance is paused anyway, so idle members do not tie up global capacity for hours.
    - The worker resumes with `start_immediately` (`UsageLimitRecoveryWorker.ts:58-68`), outside
      admission. When the continuation run starts, the member takes a global slot again even if that
      briefly exceeds the cap; the overshoot is logged as a count only.
    - The delegated task was already finalized as `failed` on the limited run. So the envelope,
      verify, and release come from the continuation run, bound through
      `usageLimitContinuationOfRunId` (SW-A6 run binding).
  - **Auto-resume off:** the member becomes `failed` (class `usage_limit`), and `swarm_retry` is the
    way back.
- **Instance down (rev 3, moved from SW-B7).** On the 2026-11-04 local run, five OpenCode members
  failed at once. Without a pause, the scheduler keeps admitting queued rows onto a broken instance,
  and each fails within seconds.
  - **Trigger:** two or more members on one instance end with `transport_error` or
    `provider_error` within 60 s.
    - It is read from `last_failed_instance_id`, `last_failure_class`, and `last_failed_at`
      through their index (§4.4), across all swarms.
    - These columns are written on every failure and are not cleared when a row is requeued
      (rev 3.1), so a retry does not erase the history.
    - The check runs in the same transaction that records the failure, **before** any automatic
      retry is scheduled.
  - **Action:** pause admissions on that instance for 5 minutes, with `pause_class` `instance_down`
    in `swarm_instance_pauses`, and send one note per swarm that has members on the instance.
    `anyOf` members move to the other instances (SW-A3b).
  - A failure of the same class within 5 minutes after the pause ends pauses it again for 15
    minutes. Pauses never stack beyond that.
- **Automatic retry (rev 3).**
  - **Eligible:** a member that fails with `transport_error` or `provider_error`, whose provider
    failure is not marked `retryable: false` (`OrchestrationV2ProviderFailure.retryable`,
    `orchestrationV2.ts:1432`).
  - **What happens:** it is retried **once**, through the `swarm_retry` path (`attempt + 1`, the
    previous envelope as data, the swarm-admission dispatch). It is not released in between.
    - `retry_after` is set to 30 s plus up to 15 s of jitter, and the row is `queued` with reason
      `retry_after:<at>`.
    - A paused instance also has to resume first.
    - An `anyOf` member is placed again, preferring another instance.
  - The retry counts toward the 48 total and `maxTotalTurns`; with neither left, the member stays
    `failed`.
  - The server setting `swarmAutoRetryTransient` (default `true`) turns it off.
  - `auto_retries` records it, and the panel shows "retried automatically".
  - In one transaction (rev 3.1): record the failure, run the instance-down check, increment
    `auto_retries`, set `retry_after`, requeue, and move the old task to `superseded_task_id`
    (SW-A7). The writer check (SW-A3) runs first.
- **Other failures:** the member becomes `failed` with its class and is released at once under the

  used or is not allowed.

**SW-A9. Limits (1.75 d; rev 3 adds 0.5 d for `maxTotalTurns`; rev 3.1 adds 0.25 d).**
- **`maxTurns`:** counted from the child's runs, including verify retries and follow-ups. Exceeding
  it calls `stopMember`, with class `budget`.
- **`maxWallClockMs`:** measured from `started_at`, or from the latest follow-up's dispatch.
  Exceeding it is handled the same way. This includes a member in `limit_wait`: `stopMember`
  disarms its continuation first (SW-A7, rev 3.1).
- **`maxTotalTurns` (rev 3).** This caps the whole swarm: with the per-member defaults alone, 48
  members could use 960 turns plus retries.
  - **Counted:** the sum of `turns_used` over all members and attempts, including verify retries,
    follow-ups, automatic retries, and unbound runs before release.
  - **When it is reached:** `budget_exhausted` is set on the swarm.
    - Queued rows become `cancelled` with class `budget`.
    - Running members finish their current run. Their verify still runs, but no verify retry, no
      follow-up, and no automatic retry starts.

      "budget: no retry" (rev 3.1).
    - Members in `limit_wait` go through `stopMember`, which disarms the continuation, because the
      worker would otherwise resume them outside admission (rev 3.1).
    - One note is sent (`swarm-note:<swarmId>:budget:<seq>`).
    - `swarm_add_members`, `swarm_followup`, and `swarm_retry` fail with `invalid_request`
      ("swarm turn budget used").
  - **Default:** the setting `swarmDefaultMaxTotalTurns` (default 240, settings range 1-2,400). The
    swarm value can only lower it.
- **Defaults:** the settings `swarmDefaultMaxTurns` (default 20) and `swarmDefaultMaxWallClockMs`
  (default 2 h). A member value can only lower them.

Fork commit: `02f0f619f5` feat(swarm): verify members in their checkout before release (SW-A6).

**Runner:**

- `swarm/SwarmVerifier.ts` (the `SwarmVerifier` service):
  - `checkoutOf(thread)`: the child thread's `worktreePath ?? project.workspaceRoot`, via
    `ProjectService.getById`;
  - `run({ argv, cwd, timeoutMs })`: `runBounded` with 16 KB tails, returning
    `{ passed, exitCode, timedOut, outputTail }`. The tail is stdout then stderr, cut to the
    last 4,096 characters. A spawn failure is a failed check.
  - Output goes only into the envelope and the retry message, never into logs.
  - server.ts provides it with `RuntimeLayer.layerProjectService`, as it does for `PeerExec`.

**Policy:**
- **Create time:** the existing check stays: the architect's mode and the member's resolved
  ceiling must both be `auto` or `full-access`, and `plan` members are refused. The `notYet`
  refusal is lifted. `verify` (the member's own, else the swarm default) is stored in the spec as
  `verifyArgv`, `verifyTimeoutMs`, and `verifyMaxRetries`.
- **Run time:** before every check, the architect thread's `runtimeMode` and the child thread's
  `runtimeMode` are read again. If either no longer allows verify, the member ends
  `claimed_done` with the new envelope field `verifySkipped: "runtime_mode"`. That field is a
  contract addition, optional, and is also shown in the digest. An unresolvable checkout gives
  `verifySkipped: "no_checkout"`.
- A check never starts while any run on the member thread is active.
- Shared-checkout members verify one at a time per checkout, using a semaphore per `cwd`.

**Flow (`reconcileMember`, `ensureVerify`, `applyVerifyOutcome`):**
- When the bound run completes and the member has verify, the member becomes `verifying`, which
  keeps its slot. The check runs on its own fiber (a `FiberMap` keyed by member), outside the pass
  lock.
  - The fiber records the outcome in memory while it still holds the checkout lock, then wakes
    the scheduler.
  - The next pass applies the outcome first, under the pass lock.
  - A result is discarded if the row is no longer `verifying`, if the attempt or bound run
    changed, or if a run started meanwhile.
  - A `verifying` row with no fiber (after a restart) starts its check again.
- **Pass:** `verified`, with `envelope.verify` (`passed`, `exitCode`, `timedOut`, `attempts`,
  `outputTail`). It is then released through the SW-A5 path.
- **Fail with retries left (default 2):**
  - The row is written first: `verify_attempts + 1`, status `running`, `bound_run_id = null`,
    and an envelope that holds the failed check.
  - Then `message.dispatch` goes to the member's thread:
    - command id `swarm-verify:<swarmId>:<key>:<n>`, message id `message:` plus that id;
    - `queue_after_active`, `createdBy: "agent"`, `creationSource: "server"`;
    - the text has the command, the exit code or "It timed out.", and the last 2,048 characters
      of output.
  - The message is not sent unless the swarm row is still `active`, read just before the dispatch.
    If the swarm is no longer active, the member fails instead.
  - The delegated task is not reopened. The held wake is released once, at the end.
- **Fail with no retries left:** `failed`, `failure_class = verify`, with envelope `failure` class
  `verify`.
- A run that ends `failed` or `interrupted` skips verify, as before.

**Run binding (rev 2.1):**
- The bound run is:
  - `bound_run_id`;
  - else `child_run_id` for the first attempt;
  - else the run whose `userMessageId` is the current retry's message id. It is stored as
    `bound_run_id` once seen.
- A usage-limit continuation (`limit-resume:<threadId>:<runId>:…`, `UsageLimitRecoveryWorker`) of
  the bound run is followed. The run record does not carry `usageLimitContinuationOfRunId`, so the
  link is by message id. Until SW-A8 adds `limit_wait`, a usage-limit failure ends the member
  first, so this path is dormant.
- A retry whose message started no run yet is dispatched again on the next pass (same command
  id).
- Any other run on the member thread never ends an attempt. Before release, `turns_used` follows
  the thread's run count.
- **Verify races:** a run that starts during a check removes the fiber, which kills the process
  tree. The member goes back to `running` with the same bound run, and the check runs again once
  the thread is idle. A verify command whose member was cancelled or detached is removed on the
  next pass.

### SW-A7 status, cancel, retry, collect, follow-up, and recovery (2026-11-05)

Fork commit: `40fe2c62f8` feat(swarm): add swarm status, cancel, retry, collect, and follow-up
(SW-A7). It sits on top of the review fixes above.

All five tools are real now. Each one is allowed only from the thread that created the swarm. Any
other thread, or an unknown swarm id, gets the same `capability_denied`, so swarm ids cannot be
probed. Each tool refuses while the flag is off, as before.

**`swarm_status`:**
- The `digest` view (the default) has:
  - `byStatus`;
  - `byQueueReason`, keyed by the reason's kind before its `:`;
  - per instance: active members (those holding slots), the cap from `instanceCap`, and
    `pausedUntil` and `pauseClass` for a live pause. There are at most 8 instances, busiest
    first, then id, with `moreInstances` for the rest;
  - `turnsUsed`, `maxTotalTurns`, and the final and released counts.

  Measured: 10 members over 9 instances come to under 1 KB.
- The `members` view returns pages of member results with no envelopes (default 25). It returns
  `nextOffset`, or `null` on the last page.

**`stopMember(swarm, member, reason)`** (internal; `reason` is `cancel`, `stop`, or
`closed_thread`):
- **`limit_wait` members** are disarmed first. The command is `thread.metadata.update {
  limitRecovery: { runId: latestRunId, resetAt: usageLimitResetAt, autoResume: false } }`,
  with id `swarm-disarm:<swarmId>:<key>:<attempt>`.
- **Stopping:**
  - any running check is killed;
  - then `thread.stop` on the child (`stopDelegatedTasks: false`), followed by
    `stopDelegatedTasks` for its subtree, both with id `swarm-stop:<swarmId>:<key>:<attempt>`.
- **The member ends `cancelled`** with an envelope:
  - built from its bound run;
  - or an empty one when no bound run exists, so a held task can still be released;
  - Stop sets class `cancelled_by_architect_stop`.
- Logs carry ids and the reason only.

**`swarm_cancel`:**
- Runs under the pass lock.
- Each key is handled by state:
  - unknown: `not_found` in `notCancelled`;
  - already cancelled: listed in `cancelled`, so a retried call repeats its answer;
  - otherwise final: `already_final`;
  - never launched: becomes `cancelled`;
  - launched: the MCP `assertStoppable` check runs first, the same rule as `task_cancel`, walking
    the member's subtree. A failure goes to `notCancelled` with its code, for example
    `runtime_mode_escalation_denied`. Otherwise `stopMember(cancel)`.
- With no keys the swarm becomes `cancelled`.
- The pass then releases cancelled members with their `"status":"cancelled"` digests while the
  cohort is open; this is tested.
- A detached swarm is refused.

**Architect Stop (rev 3.4, §4.6):** `closeSwarm` for `stopped` and `closed_thread` now calls
`stopMember` for every launched, non-final member, along with cancelling the queued rows. Its
command ids are the same ones the cascade or a repeat would use, so a repeat is idempotent.
- The "reactor" is the pass itself. It is woken by `run.updated` on watched threads (architects
  and members) and by the 5 s tick, and it reads only the anchor's `disposition`. At startup it
  recomputes from the store, so no separate reactor fiber was added.

**`swarm_retry`:**
- Refused when:
  - the swarm is not `active` or `completed`;
  - its budget is exhausted;
  - the anchor's disposition is not `open`;
  - a target sets `environmentId` or `projectId` (remote, D11);
  - a target sets `anyOf` (deviation: omit `target` to place an `anyOf` member again);
  - a member is not `failed` or `cancelled`;
  - a member still has a `superseded_task_id`;
  - the attempts would go over 48 (D5: `Σ attempt + retries`);
  - the SW-A3 writer check fails, counting the retried members as non-final.
- **A new target:**
  - is resolved once, through the resolver;
  - the old ceiling steps down to what the new instance offers (`resolveRuntimeMode(ceiling,
    undefined, target)`);
  - verify needs `full-access` there (B1);
  - `anyOf` is dropped from the spec.
- **Requeue:** a single row update sets:
  - `attempt + 1` and status `queued`;
  - every child, task, run, envelope, and placement field cleared;
  - `verify_attempts`, `followups`, `followup_notified`, and `released` reset;
  - `superseded_task_id` = the old task if it was never released;
  - `spec.previousAttempt`.
- **`spec.previousAttempt`** wraps the previous attempt's facts as JSON data, with `<` escaped,
  under "Previous attempt (context reset)": status, failure class, summary, decisions, and the
  verify tail. Admission puts it before the task.
- Then `admitNow`. A `completed` swarm reopens.
- A retried `anyOf` member avoids the instance its last attempt failed on (`avoidInstanceId`),
  unless that is the only candidate. This was deferred from SW-A3b.

**`swarm_collect`:**
- Returns final envelopes, including detached ones, ordered by `ended_at`, then key.
- The cursor is `<ended_at>~<key>`. With no new results, `nextCursor` echoes `since`. A bad cursor
  is `invalid_request`.
- `keys` narrows the members.
- `fields` narrows each envelope, but `status`, `attempt`, `followup`, and `structured` always
  come. `failure` also always comes, which is a deviation: it is small and qualifies the status.
  - `verify` adds `verifySkipped`;
  - `artifacts` adds `testFilesChanged`;
  - `data` adds `dataDropped`.
- `maxBytes` defaults to 16 KB. An envelope over `maxBytes` on its own comes alone, with `data:
  { omitted: true }`.
- A follow-up's new envelope moves its `ended_at`, so it appears again after the cursor.

**`swarm_followup`:**
- **Allowed** for `claimed_done`, `verified`, or `failed` with class `verify`, in an `active` or
  `completed` swarm without an exhausted budget.
- **Refused** for:
  - running, verifying, launching, queued, and `limit_wait` members ("follow up once it has
    finished");
  - other final members ("use swarm_retry");
  - a member after 5 follow-ups;
  - a member that never started;
  - the SW-A3 writer check.
- `maxTurns` is still refused at create, so there is no turns check yet (SW-A9).
- **`clientRequestId`:** stored as `spec.followupRequestKey`, and a repeat returns the same
  follow-up.
- **Order, all under the pass lock:**
  1. Reopen a `completed` swarm first.
  2. Write the row: `followups + 1`, `running`, `bound_run_id = null`, `verify_attempts = 0`
     (fresh retries), `followup_notified = 0`, a cleared failure class, and
     `spec.followupText`.
  3. Dispatch to the member's thread with id `swarm-followup:<swarmId>:<key>:<attempt>:<n>`.

  The message wraps the architect's text in `<swarm-architect-message>` and adds the
  result-block reminder.
- **Binding:** the bound run is the run whose `userMessageId` is that message, through the general
  pending-message rule:
  - a verify retry if `verify_attempts > 0`;
  - else a follow-up if `followups > 0`;
  - else the admission run.
- **Delivery:**
  - **Unreleased member:** the new envelope replaces the old one and goes out in the normal held
    release, which also sets `followup_notified`. There is no note.
  - **Released member:** once the member is final, `queueFinishedFollowups` puts `(key, n)` in
    the outbox unless an unsent row already has it. That gives one note per follow-up after the
    5 s window, and the held wake is not released a second time.
- **Recovery:** a running follow-up with no run gets its message re-sent by the next pass.

**Ids (deviation):** verify retry ids are now `swarm-verify:<swarmId>:<key>:<attempt>:<followup>:<n>`,
and follow-up ids carry the attempt too. The plan's `<key>:<n>` would collide across attempts and
follow-ups: the orchestrator's receipt would replay the old command and send nothing new.

- `superseded_task_id`: disposed once terminal (SW-A5 path; tested with `swarm_retry`).
- A stored placement: SW-A3b.

### SW-A9 limits (2026-11-05)

Fork commit: `b304e07c85` feat(swarm): enforce member turn and time limits and the swarm turn budget
(SW-A9).

**Refusals lifted.** `maxTurns`, `maxWallClockMs`, and `maxTotalTurns` are accepted now.
- Member values are lowered to the settings `swarmDefaultMaxTurns` (20) and
  `swarmDefaultMaxWallClockMs` (2 h), and stored in the spec.
- A swarm's `maxTotalTurns` above `swarmDefaultMaxTotalTurns` (240) is `invalid_request`.
  Otherwise the effective value (the input, or the setting) is stored in `swarms.max_total_turns`
  and shown by `swarm_status`.

**Counting.**
- `turns_used` is `spec.priorTurns + the member thread's runs`. It is counted on every reconcile
  of an unfinished, non-detached member, including runs before release, verify retries,
  follow-ups, and continuations.
- `requeuePatch` (`swarm_retry` and the automatic retry) carries `priorTurns = turns_used`, so the
  total survives a new attempt.
- `maxTurns` compares only this attempt's runs.

**Enforcement** (`enforceLimits`, each pass, active swarms, after reconcile):
- **A member** past `maxTurns`, or past `maxWallClockMs`, is stopped through `stopMember` with
  the new reason `budget`, ending `cancelled` with class `budget`.
  - The wall clock runs from `started_at`, now set when the child is created at admission. A
    follow-up's `spec.followupStartedAt` restarts it.
  - A `limit_wait` member is stopped the same way, disarming its continuation (SW-A7).
- **The swarm:** when `Σ turns_used ≥ maxTotalTurns`:
  - the swarm is marked `budget_exhausted`;
  - queued rows become `cancelled` with class `budget`;
  - `limit_wait` members go through `stopMember`;
  - running members finish their current run;
  - no automatic retry starts (SW-A8 already checks `budget_exhausted`);
  - a verify retry is not sent, and a final verify failure ends `failed` (class `verify`) with
    "budget: no retry" in its failure message;
  - follow-ups are refused;
  - the existing `budget` note goes out once, on the next pass;
  - admissions stop (`admits` also checks `budget_exhausted`);
  - `swarm_add_members`, `swarm_followup`, and `swarm_retry` refuse with "swarm turn budget
    used".
- **The member's turns** are checked in two more places:
  - a verify retry that would exceed `maxTurns` is not sent ("budget: no retry");
  - `swarm_followup` is refused when the member already used `maxTurns` turns (rev 3.1).

**Docs:** `docs/user/swarm.md` gains "Limits". The change only adds lines.

## 10. Rationale and research (summary)

The full research pass is in git history (`d0e5a3b`).

- **Verify before trusting "done" (SW-A6).** In the MAST taxonomy (1,600+ failure traces), about 24%
  of failures are verification failures, and objective verification gave +15.6%. The Anthropic
  parallel C compiler depended on near-perfect tests.
- **Small, decomposable teams with one hub (D5, SW-A10).** Google Research measured +81% for
  parallel work and −39-70% for sequential work, and 4.4× error amplification with a central
  orchestrator against 17.2× without one. Local runs came in waves of 5-14.
- **Cost scales with tokens (SW-A9).** Anthropic's research system used about 15× the tokens of a
  chat. Revision 3 bounds it per swarm with `maxTotalTurns` and keeps the architect's context small
  with compact wake details and `batch` (SW-A5), because the orchestrator's context is the shared
  bottleneck of a hub design.
- **Best-of-N needs a verifier (SW-B1).** Large Language Monkeys (*unchecked*) and Cursor's
  `/best-of-n`.
- **Isolated work plus a merge gate beats locks (SW-B2).** Cursor's scaling write-up.
- **Capacity comes from more accounts, not more agents per account (SW-A3b).** Per-instance limits
  and usage windows are what bound throughput. Spreading across accounts at admission time is the
  only way to use them together, and the SW-A11 three-account run measures it.
- **Not planned:** member-to-member messaging, a shared board, and debate. Architect-to-member
  follow-ups (`swarm_followup`) stay inside the hub model.

## 12. Changes in revisions 2 and 3

- **Launch (blocker).** Revision 1's deferred `preparing` children would have been cancelled by
  restart reconciliation, cascaded by Stop, and shown as live runs. They are replaced by queued rows
  plus a swarm-admission dispatch against the recorded anchor run (§4.2). The spike was rewritten
  around restart, Stop, and late admission.
- **Stop and cancel (blocker).** The Stop, detach, and cancel model (D12, SW-A7) was added. Notes
  now go through `notifyArchitect` instead of the disposed cohort. `stopMember` was added for callers
  without an MCP scope.
- **Release mechanics.** Release now goes through `wake-policy` with a stored `completionDetail`. It
  re-plans when `completionDelivery` is unset, treats a same-value request as a no-op, and has a held
  check before cohort logic. Both successor collectors are covered.
- **Verify retries** are driven by `SwarmService` watching the child's next run; the task is not
  re-opened. Verify runs on a shared `boundedExec` taken from `PeerExec`, not `ProcessRunner`. The
  runtime-mode rule is stricter (`auto` or `full-access` for both threads).
  Decision 2026-11-04 (review B1): stricter still, `full-access` for both threads.
- **Approvals** go to the user, with a coalesced note to the architect. There is no `"approval"`
  request kind.
- **Scope.** Remote members are refused in Phase A. Quorum, the instance-down heuristic, and
  `maxSummaryBytes` moved to Phase B.
- **Fact corrections:**
  - `isBetween` takes an object form.
  - `OrchestratorMcpTitle` needs exporting.
