### 4.2 Launching after the architect's turn has ended

The problem has two parts:
- `delegateTask` requires the architect's run to be active (`parent_not_active`,
  `OrchestratorMcpService.ts:2283-2295`).
- `dispatchDelegatedTaskRequest` (`Orchestrator.ts:7200`) refuses a parent run that is not blocking
  (7227), that is stopping (7234), or whose node does not belong to it (7242-7253).

The architect ends its turn right after `swarm_create`, so a member that waits for a free slot
cannot be launched through today's path.

Revision 1 proposed registering every member as a deferred child parked in `preparing`. That is
dropped, because the review found:
- Restart reconciliation cancels `preparing` runs (`ProviderRuntimeRecoveryService.ts:86-95`, 219,
  468-477).
- A Stop on the architect cascades to them.
- They count as live runs (`Orchestrator.ts:643-645`), so they flood Working and show "Preparing
  workspace".
- `defer_start` without a workspace strategy is unsupported (`Orchestrator.ts:7419-7422`,
  `ThreadLaunchService.ts:1071-1072`).

**Design (revision 2): queued members do not exist in the orchestrator until they are admitted.**
- **Queued members are only rows.** A queued member is a row in `swarm_members`. Nothing about it
  exists in the orchestrator, so restarts and Working are unaffected.
- **The anchor run.** At `swarm_create`, the server records an anchor: `parentThreadId`, the
  architect's current `parentRunId`, and that run's `rootNodeId`. Members that fit the caps are
  launched right away through today's path while the run is live.
- **Late admission.** Later admissions dispatch `delegated_task.request` through a new
  **swarm-admission** variant. The command gains an optional `swarmAdmission: { swarmId }` field
  (contracts `orchestrationV2.ts` ~3290). It is accepted only when **all** of these hold:
  - `createdBy: "server"`;
  - the parent run is the anchor run recorded for that swarm (the orchestrator checks it against the
    command, and `SwarmService` is the only issuer);
  - the anchor run's `delegatedCompletion.disposition` is `open`, or is unset because no member has
    finished yet;
  - the anchor run was not stopped, which `stopReachedRun` already reports;
  - the parent thread is not archived or deleted;
  - the parent node belongs to the anchor run.

  The `isBlockingRun` check is skipped only for this variant. Everything else in the dispatch is
  unchanged: the subagent row, lineage, the cohort on the anchor run, and the child message.
- **A durable anchor marker (rev 2.1).** The orchestrator cannot read `SwarmStore`, so the anchor
  must be recorded in orchestrator state.
  - `swarm_create` dispatches a new `swarm.anchor { swarmId }` command while the architect's run is
    live. It records the `swarmId` on the anchor run (`delegatedCompletion.swarmIds`, added to the
    run contract next to `orchestrationV2.ts:621-625`). This happens even when no member can be
    admitted at once, for example when every target instance is paused.
  - A swarm-admission dispatch requires its `swarmId` to be present on the anchor run.
- **Strip the field from clients (rev 2.1).** `withCreationProvenance`
  (`ThreadManagementService.ts:84-86`) already overwrites `createdBy` for client commands. It must
  also strip `swarmAdmission`, the way `linkOrigin` is stripped. That way a WebSocket client
  (`ws.ts:1876-1905`) cannot forge a late admission.
- **Stop on any later run (rev 2.1).** `stopReachedRun` sees only a `run_interrupt_request` on the
  anchor run itself, and `thread.stop` marks the run it interrupts or the latest executed run
  (`Orchestrator.ts:11356-11364`). A Stop during a later architect turn therefore never reaches the
  anchor. So the admission guard also refuses when **any** run on the parent thread with an ordinal
  at or above the anchor's carries a `run_interrupt_request` turn item. This is checked under the
  parent lock, so a concurrent Stop cannot race it.
- **Failed anchor run.** If the anchor run ends `failed`, for example on a provider error right
  after `swarm_create`, admission continues. The members' work is independent of the architect's
  turn, and completions still wake the architect. A test pins this behavior.
- **Modes at admission.** The runtime and interaction modes are re-resolved against the architect
  thread's **current** modes (`delegatedTaskModes.ts`). A member never starts with more than the
  architect has now.
- **Ordering.** Admission dispatches take the parent lock (`threadDispatch.withLock`,
  `Orchestrator.ts:13052-13072`) one at a time, as today. The child's `prepareRun` and its first turn
  run outside the lock.
- **Retries.** `swarm_retry` and the panel's Retry use the same admission path, so they work with no
  live architect run.

### 4.6 What `SwarmEventReactor` watches

The reactor subscribes to `engine.streamDomainEvents`, the same source as
`DelegatedTaskQuestionReactor`. It filters to the threads of swarm members (by `child_thread_id`)
and the architect threads of active swarms. It handles:
- **Child `run.updated`:**
  - `running` → member `running`.
  - Terminal → the member terminal path (SW-A5/A6).
  - A failed `prepared-run.fail` frees the member's slot.
- **Architect thread:**
  - A `turn-item.updated` of type `run_interrupt_request` on any run at or after the anchor, or the
    anchor cohort `disposition` becoming `stopped` → cancel the swarm (D12). `thread.stop` is a
    command, not a domain event, so the reactor cannot watch it directly. At startup, the reactor
    recomputes this check for every active swarm, because its in-memory state is lost on restart.
  - The cohort becoming `disposed` through a user cancelling a queued wake (`Orchestrator.ts:9284`) →
    detach the swarm (D12).
  - Archive or delete → cancel.
- **Settings changes** to caps or the flag → the scheduler re-evaluates. If the flag is turned off,
  nothing new is admitted. Running members continue, and the panel still shows them.

  - Verify is allowed only when **both** the architect's and the member's effective runtime modes
    are `auto` or `full-access` (`RuntimeMode`, `providerPolicy.ts:25-30`). Under

## 6. Item 3 — Phase B tasks (each ships only if qualified)

**SW-B1. Race mode (3 d).**
- `swarm_create({ race: { task, title, attempts: [{ target }] (2-5), verify, select:
  "first_verified" | "all_then_compare" } })`. It cannot be combined with `members`.
- `verify` is required.

  `swarm.act({ action: "pick" })`.

**SW-B2. Integration check and collision detector (3 d).**
- **Overlap warnings:** overlapping `ownsPaths` between writers come back as `warnings` in the
  `swarm_create` result.
- **`swarm_integrate({ swarmId, keys?, verify? })`:**
  - Creates `t3/swarm-<id>-integration` from `base_commit` in a scratch worktree.
  - Merges the member branches in ordinal order and stops at the first conflict, which it reports.
  - Runs verify on the merged result.
  - Never touches the user's branch.
- **Collision detector:** two or more members sharing 3 or more changed paths outside their
  `ownsPaths`, or the same failing test id in their verify tails, pause admissions for that swarm.
  The architect gets a note.

## 10. Rationale and research (summary)

The full research pass is in git history (`d0e5a3b`).

- **Verify before trusting "done" (SW-A6).** In the MAST taxonomy (1,600+ failure traces), about 24%
  of failures are verification failures, and objective verification gave +15.6%. The Anthropic
  parallel C compiler depended on near-perfect tests.
- **Small, decomposable teams with one hub (D5, SW-A10).** Google Research measured +81% for
  parallel work and −39-70% for sequential work, and 4.4× error amplification with a central
  orchestrator against 17.2× without one. Local runs came in waves of 5-14.
- **Cost scales with tokens (SW-A9, SW-B10).** Anthropic's research system used about 15× the
  tokens of a chat.
- **Best-of-N needs a verifier (SW-B1).** Large Language Monkeys (*unchecked*) and Cursor's
  `/best-of-n`.
- **Isolated work plus a merge gate beats locks (SW-B2).** Cursor's scaling write-up.
- **Not planned:** member messaging, a shared board, and debate.

## 11. Risks

| Risk | Mitigation |
| --- | --- |
| The swarm-admission dispatch against a completed anchor run misbehaves (SW-A0) | The fallback admits on the architect's next run, with documented latency |
| A `"held"` wake is never released | Release on every terminal path (verify, failure, `stopMember`, budget, recovery); a start-up sweep releases held tasks of final members; `released` column; tests for each path |
| Release lands on a disposed or stopped cohort | Expected under D12. A note is sent through `notifyArchitect`, and the panel and `swarm_collect` keep the results |
| Verify is an agent-chosen process | Allowed only in `auto`/`full-access` for both threads, re-checked before each run; argv with no shell; timeout and tree kill; never runs alongside the member's run; output not logged |
| Usage-limit continuation and the scheduler disagree | The continuation owns the member; the scheduler only pauses new admissions (SW-A8) |
| Orchestrator contract changes (`swarmAdmission`, `"held"`, `completionDetail`) collide with v1.2.0 | Keep them additive and optional; rebase after each v1.2.0 orchestrator commit; record them as fork contract changes in the release notes |
| Many live children crowd the Working section | P2-1 measures it. Queued members are not threads under the revision 2 design; follow-up is a "fold children under the parent" option, out of scope here |

## 12. Changes in revision 2 (from the review)

- **Launch (blocker).** Revision 1's deferred `preparing` children would have been cancelled by
  restart reconciliation, cascaded by Stop, and shown as live runs. They are replaced by queued rows
  plus a swarm-admission dispatch against the recorded anchor run (§4.2). The spike was rewritten
  around restart, Stop, and late admission.
- **Stop and cancel (blocker).** The Stop, detach, and cancel model (D12, SW-A7) was added. Notes
  now go through `notifyArchitect` instead of the disposed cohort. `stopMember` was added for callers
  without an MCP scope.
- **Release mechanics.** Release now goes through `wake-policy` with a stored `completionDetail`. It
  re-plans when `completionDelivery` is unset, treats a same-value request as a no-op, and has a held
  check before cohort logic. Both successor collectors are covered.
- **Verify retries** are driven by `SwarmService` watching the child's next run; the task is not
  re-opened. Verify runs on a shared `boundedExec` taken from `PeerExec`, not `ProcessRunner`. The
  runtime-mode rule is stricter (`auto` or `full-access` for both threads).
- **Approvals** go to the user, with a coalesced note to the architect. There is no `"approval"`
  request kind.
- **Scope.** Remote members are refused in Phase A. Quorum, the instance-down heuristic, and
  `maxSummaryBytes` moved to Phase B.
- **Fact corrections:**
  - `isBetween` takes an object form.
  - `OrchestratorMcpTitle` needs exporting.
  - The budget test lists all registered tools, so it must filter by `EnabledWhen`.
  - The `worktreePath` expression is at 2323, and the verifier needs the child's own path.
  - `swarm_members` needs `command_id` and `child_run_id`.
  - `resultThreadIds` and `t3ToolSummary` read `launched`.
  - Mobile uses `PAGE_PROJECT_KEYS`.
  - `collectLimitPools` groups by driver.
  - `thread-sidebar.md:77` is stale.
  - `dev-t3-serve.sh` is in the bridge repo.
  - The fleet RPCs also touch `rpc.ts` and `fleetUpdate.ts`.
  - The restore-defaults line numbers were corrected.
