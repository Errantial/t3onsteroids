## Root cause

The sync task was a one-off support workaround, created outside every repository (the Framework
copy lives in `C:\Users\Emil\apps\t3code-service\`, the laptop copy in `C:\Users\emilg\.t3\`).
It existed because the fork desktop passed its full version to the SSH runner:

```text
0.1.5-v1.1.4.20261031.98beeb3e80fd.connect1
```

while the runtime archive is published under the base tag:

```text
https://github.com/pingdotgg/t3code/releases/download/v0.1.5/t3-0.1.5-linux-x64.tar.gz
```

`HEAD` on that URL returns `200`, `Content-Length: 123004975`.

The window came from the task action itself, which ran a console program in the interactive
session. Framework before:

```xml
<Interval>PT1M</Interval>
<Command>powershell.exe</Command>
<Arguments>-NoProfile -NonInteractive -ExecutionPolicy Bypass -File C:\Users\Emil\apps\t3code-service\remote-runtime-sync.ps1</Arguments>
```

Laptop shape (read over SSH):

```text
Execute: C:\Users\emilg\.t3\remote-runtime-sync.cmd
Interval: PT1M
```

## Fix

- `remoteRuntimeReleaseVersion()` (packages/ssh) strips the fork suffix before the archive version
  is chosen. Stock and nightly versions pass through unchanged.
- `apps/desktop/src/remoteRuntimeSyncMigration.ts` rewrites the task once at app start. It writes
  `<script dir>\remote-runtime-sync-hidden.vbs` and points the task at
  `wscript.exe //B //Nologo "<vbs>"`, then sets the repetition to `PT15M`. The VBS starts the
  original command with window style `0` and does not wait.

## Linux build and server-1 update

The Linux artifact is `t3-<full>-linux-arm64.tar.gz`, built natively on the aarch64 host with Node
26.12.1. Its `t3` is a launcher that runs the bundled server (`t3.mjs`) with the shipped Node
binary; Node 26.12.1's SEA output would not execute on this host (`--build-sea`, `vp pack` and
postject-injection all returned `ENOEXEC`, while the stock Node binary runs), so the runtime ships
the working layout instead of the SEA. `update-release-package-versions.ts` set the workspace
version before bundling, so `t3 --version` reports the release.

server-1 update through `scripts/fleet-update.mjs --tag v1.1.5 --targets server1 --yes`:

```text
before=t3 v0.1.5-v1.1.4.20261031.98beeb3e80fd.connect1
old=/home/opc/.t3-nightly/runtime/versions/0.1.5-v1.1.4.20261031.98beeb3e80fd.connect1
new=/home/opc/.t3-nightly/runtime/versions/0.1.5-v1.1.5.20261031.d43ad80f4724.connect1
http=200
t3 v0.1.5-v1.1.5.20261031.d43ad80f4724.connect1
```

Afterwards: `systemctl --user is-active t3code` = `active`, `ExecStart` points at the v1.1.5
directory, `http://127.0.0.1:3773/` = 200, `t3code-mcp.service` still active on :3774 (401 without
auth, as before). The v1.1.4 directory is retained for rollback.

`latest` channel, `allowPrerelease=false`) sees it on its next update check and downloads the
installer named in the manifest.
