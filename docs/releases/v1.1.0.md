# t3onsteroids v1.1.0

The latest full release of the t3onsteroids bridge, rebuilt on **T3 Code v0.1.5** and combining the post-v1 feature line with the T3 provider usage/tokens-sec patch series.

## Highlights

- **Two concurrent bridged chats.** A durable, profile-wide admission scheduler replaces the single-slot lease: bounded active set, durable FIFO queue, exact queued cancellation and slot reuse across processes. `supportedConcurrency=2` is advertised from the passing isolated eight-case two-chat matrix.
- **Workspace and worktree binding.** `provider-session-workspace-v1` resolves exact project roots, linked Git worktrees and project subdirectories to one owning CoS project; the workspace is stored immutably on the session and revalidated on every prompt.
- **Model and reasoning selection.** `provider-model-catalog-v1` publishes the controller model catalog; the bridge advertises model/thought-level ACP config options, persists the choice, and fails a send whose picker does not confirm it.
- **Prompt images.** PNG/JPEG prompt attachments are converted to bounded WebP before delivery; every unsupported format or controller without `provider-input-images-v1` fails closed with `unsupported_prompt_content`.
- **Background-work projection.** `provider-background-work-v1` projects native CoS workers, fences settlement on pending work, and supports report-after-drain follow-ups so native work can finish after the provider turn without being silently lost.
- **Multiplexed provider event streams.** `provider-event-stream-mux-v1` gives the bridge a shared stream budget for concurrent sessions (used by the two-chat lane; four-chat remains parked).
- **Durable recovery hardening.** Exact-generation cancellation, restart/drain reconciliation, stale-event isolation, and bounded polling scaled to the admission capacity remain in force.

## Built on T3 Code v0.1.5

The bridge targets T3 Code `0.1.5` (`6d450a4284852af137b2f3407fddd89eb76e7644`). The T3-HEAD acceptance lane additionally exercised `dd14848…` (0.1.6 nightly): protocol probe, headless single/multi-turn, restart/resume, worktree and linked-worktree, UI text, and UI image attachment.

Upstream v0.1.5 features inherited by this baseline include No-project-to-project conversion, Antigravity Claude/GPT model and thinking controls, configurable thread-details cards, fleet Stable/Nightly switching, guest-link diff protection, and the Electron/Brotli security fix.

## T3 patch series

The maintained series in `handoff/t3-patches/` applies to both the pinned `ffb4af8d` v1.0.0 tuple and T3 `0.1.5`:

1. `feat(web): optional per-thread tokens/sec readout` — off by default, per-thread toggle, provider-reported tokens only.
2. `feat(acp): report per-turn token usage from the prompt response` — maps ACP `session/prompt` usage into normalized `TurnTokenUsage` for providers that report it.

The series is never sent upstream, and CoS threads deliberately report no token usage (the controller's token totals are estimates), so the readout stays absent for CoS by design.

## Install and launch

```text
npm ci
npm run verify
```

T3 Local ACP must launch a real Node executable with `shell:false`:

```text
C:\Program Files\nodejs\node.exe
C:\path\to\t3onsteroids\dist\cli\index.js
```

Read-only setup checks:

```text
node dist/cli/index.js --compatibility
node dist/cli/index.js --release-readiness
node dist/cli/index.js --diagnose --user-data-dir <CoS user data dir> --cwd <exact project root>
```

Real bridged prompts, pending-input cancel, and exact-turn Stop require CoS **Local control API** and **Allow actions** to be enabled by the user.

## Known limits

- Windows x64 and Node 24 are the supported production platform for this release.
- Four- and eight-chat concurrency are parked behind their own measured gates; the advertised ceiling stays at two.
- A first image turn in a freshly opened ChatGPT tab can end without the extension publishing `turn_start`/`turn_end`; retrying on the now-open conversation completes it. This is recorded as a residual in `docs/release-status.md`.
- The bridge remains same-host, same-OS-user only; remote control and cross-user scenarios are outside the supported claim.
