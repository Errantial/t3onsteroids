# t3onsteroids v1.1.7

Build commit `9e54f9846f58`; full version `0.1.5-v1.1.7.20261101.9e54f9846f58.connect1`. Assets are named with that full
version.

Fleet-wide release updates from Settings → About, the Labs pin overhaul, and Linux build hosts that
read RPM metadata instead of needing a Debian shim. This release is not rolled out; no machine was
updated.

## Fleet updates

Settings → About lists every connected machine with its platform, install variant (`Windows
desktop`, `Linux service`, or `Manual update`), current version, and the target release.

- **Confirmation first.** Nothing runs until the dialog names the machines, their current versions,
  and the target version. Both Windows and Linux restart T3 and interrupt running threads.
- **Per-machine results.** Each machine reports its own outcome. A failure does not hide the
  machines that succeeded, and the run stops at the first failure unless you choose to continue.
- **Matching artifact per variant.** A Windows desktop updates through the app's own updater and the
  `Errantial/t3onsteroids` release feed. A Linux service installs the matching
  `t3-<full>-linux-<arch>.tar.gz` release archive into `runtime/versions`, verifies it against
  `SHA256SUMS.txt`, runs the staged service preflight, and hands the switch to the boot service. A
  machine whose variant does not match an artifact is refused with a reason; nothing is inferred or
  silently swapped.
- **MCP.** `fleet_update_status` reports machines, versions, variants, reachability, and readiness.
  `fleet_update` takes `targets` (ids or `all`), `tag`, `dryRun` (default true), `confirm`, and
  `continueOnFailure`. The per-machine tools `t3_server_fleet_status` and `t3_server_fleet_update`
  let one hub drive its linked environments over the existing links; there is no second credential
  or SSH layer. Dry runs change nothing.
- **Bootstrap note.** A machine must already run v1.1.7 before About or the MCP hub can drive its
  update, because older servers do not expose these RPCs or tools. The first rollout of v1.1.7
  therefore still uses `scripts/fleet-update.mjs`; after that, updates can run from the app or MCP.

## Labs pin overhaul

The "Pinned threads on top" setting is now the Labs pin overhaul. Turning it off does both: pinned
threads sort with the activity list instead of a pinned section, and a pinned thread's Settle action
is hidden until the thread is unpinned. Turning it on keeps the previous behavior. Pinning still
prevents automatic settling, and hiding Settle is presentation only; MCP's explicit settle stays
available for automation. The earlier fold-into-Working idea remains on hold.

## Linux build tooling

`scripts/build-cli-archive.ts` records the bundled `libatomic` provenance with `dpkg-query` on
Debian/Ubuntu or `rpm` on Oracle Linux/Fedora. server-1 builds without a metadata shim, and the
shipped `lib/libatomic.so.1.LICENSE` names the package and source RPM the runtime actually carries.

## Checks

- `pnpm typecheck`, `pnpm lint`, `pnpm run knip:check`, and `node scripts/release-smoke.ts` pass.
- Bridge (`npm run verify`) on `release/v1.1.7`.
- Focused suites: fleet release helpers, thread action menu, agent context budget, Linux archive
  provenance, and the existing saved/instruction suites.
- Windows installer and Linux arm64 runtime are built from the same fork commit; the Linux archive
  is built natively on server-1 with Node 26.12.1.

## Upgrade

Windows: run the installer, or update from Settings → About. Linux: install the new runtime next to
the current one, point the unit and `runtime/service-state.json` at it, restart, and keep the
previous directory for rollback. Updating restarts T3 and interrupts running threads.

No data migration is required.
